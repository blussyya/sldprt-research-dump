# EXP-060 — The field after `Z`, the legacy Parasolid layer, and whether a fourth block exists

Date: 2026-09-21. Base: staging `e0e0c7f`.
Scripts: `scripts/EXP060/`. Reproduce: `node knowledge/evidence/scripts/EXP060/legacy-partition.js`.

Three questions, three answers. No node, entity, surface or coordinate is decoded out of the
Parasolid stream; the geometry read in §3 is DisplayLists data we already parse.

---

## 1. NQ-043 — the field is real and count-like, but it is not a topology count

### Where it lives

Only **two byte positions vary** in the 40 bytes after `Z`, across all 24 SW2022 models:

```
+0=5a +1=00 +2=02 +3=00 +4=00 [+5 +6 VARY] +7=00 +8=03 +9=00 +10=04
+11..+24 = 00 01 repeated seven times
+25..+32 = 40 8f 40 00 00 00 00 01   (f64 1000.0)
+33..+39 = 3e 45 79 8e e2 30 8c …    (f64 1e-8)
```

The `1000.0` and `1e-8` are the transmit's size box and resolution, so this is a real record
boundary, not an accidental alignment. The varying field is `u32be` at `Z+3` (its top two bytes
are always zero).

### It is not a node or topology count

`C04_cube_hole_5mm` and `C06_cube_hole_moved` have **identical topology** — same 7 faces, same
5 mm hole — differing only in the hole's position. The field differs: **316 vs 293**. A count of
nodes, faces, edges or vertices cannot change when a feature moves.

Correlation against native SolidWorks face count is high (r = 0.951) but the ratio ranges 31.7
to 68.0, so it is not a multiple of any topology count either.

### The exact relationship it does have

The text form names the field: `Z1 <value> 2 3 0 0 0 0 0 0 0 1e3 1e-8 …`. Comparing the binary
value against the text value for the same body:

| model | binary | text | difference | SolidWorks faces |
|---|---|---|---|---|
| `C00_cube_10mm` | 232 | 226 | 6 | 6 |
| `C04_cube_hole_5mm` | 316 | 309 | 7 | 7 |
| `C10_cube_shell_1mm` | 418 | 407 | 11 | 11 |
| `C13_cone` | 102 | 100 | 2 | 2 |
| `C14_sphere` | 68 | 67 | 1 | 1 |
| `C15_torus` | 45 | 44 | 1 | 1 |
| `C17_torus_quarter` | 95 | 92 | 3 | 3 |

**`binary − text == SolidWorks face count` in 24 of 24 models**, over face counts from 1 to 11.

So the binary transmit's value exceeds the text transmit's by exactly one per face. The field is
count-like and the two encodings of the same body disagree by a structured amount. What the count
counts is **not established**.

Weak supporting evidence for a node count: in `C00`'s text stream every integer from 1 to 176
appears, with 202 distinct integers ≤ 400 — consistent with node IDs running toward 226, but that
is a pattern, not a decode.

### Side finding: the binary form carries a `+1` bias on small integers

Aligning the two encodings of the same record:

| text | binary |
|---|---|
| `1` | `00 02` |
| `2` | `00 03` |
| `3` | `00 04` |
| seven `0`s | `00 01` seven times |

Every small field reads one higher in binary, consistent with 0 being reserved (null) and values
stored biased. This is direct support for the "biased numeric encoding" reading of the undecoded
trailing bytes in NQ-042 (text flag `0` ↔ binary `00 01`), and it **weakens the alternative**
proposed in EXP-059 §3 that the field splits into a `u8` flag plus a separate always-1 byte.

Note the large field does **not** follow the `+1` bias — its difference is the face count, not 1.
Two distinct effects, both recorded as measurements rather than merged into one theory.

## 2. The Parasolid layer is identical in the 2011 legacy container

The SolidWorks 2011 files are OLE2 compound documents and our DisplayLists parser rejects them.
Their **Parasolid partition is nonetheless fully readable with the existing readers**.

Extracting `Config-0-Partition` from the OLE2 directory and applying the modern-corpus readers
unchanged:

| check | result |
|---|---|
| files | 25 |
| 16-byte section magic at offset 4 | **25 / 25** |
| inner zlib inflated (28-byte header, as modern) | **25 / 25** |
| `PS` transmit header parsed | **25 / 25** |
| declaration prefix parsed | **25 / 25** |

```
schema : SCH_2201236_20000_13006   (25)
shape  : 4 declarations, Z@198     (25)
```

The section magic is byte-identical to the modern one:
`23 1d d5 71 da 81 48 a2 a8 58 98 b2 1b 89 ef 99`. The framing — 28 bytes then a zlib member —
is the same. The transmit header parses with no change. The schema base is `13006`, the same base
as every modern file.

**So the answer to "does the header that matched all 24 models match there too" is yes, exactly.**
The container changed completely between 2011 and 2022; the Parasolid layer did not.

This materially changes NQ-038. "Legacy OLE2 unsupported" is a statement about the *DisplayLists*
path only. B-rep geometry in 2011 files is reachable **today**, with code already in the
repository, and needs no legacy tessellation work first.

### Two legacy container facts, confirmed

- The legacy geometry stream is named **`DisplayLists__ZLB`**, 25/25 — the exact name recorded in
  the pre-2015 historical literature, and absent from every modern file. The historical name was
  right for its era; ours is right for ours.
- Legacy declares **`_DL_VERSION_4700`**, against 13000–17000 in the modern corpus.

## 3. There is no fourth block

Between Block3 and the forward metadata record sit 132 bytes that `parser/v0.2` skips as an
opaque prefix. If a fourth array in the `[stride, 8, 2, N]` family existed, this is where it
would be.

It is not an array. It is a per-face numeric record, and most of it is `f64` geometry **in
metres**. Decoded against `C00_cube_10mm`, a cube occupying [0, 0.01]³ m:

| face | tag | f64 values at +20…+84 |
|---|---|---|
| 0 | 4001 | 0.005 0.005 0.000 0.010 0.010 0.000 0.000 0.000 |
| 2 | 4001 | 0.005 0.005 0.010 0.010 0.010 0.010 0.000 0.000 |
| 4 | 4001 | 0.005 0.010 0.010 0.010 0.010 0.000 0.000 0.010 |

Every value is 0, 0.005 or 0.010 — exactly the cube's extents and half-extents. Across the full
corpus all 142 face prefixes are distinct and the varying words decode as `f64`, while the first
five words stay small integers.

So the region is per-face geometric metadata (plausibly a centre point plus extent or corner
values, not yet pinned down), and **no fourth block of the Block1/2/3 family exists**.

### The Block3 zeros

Block3 remains all-zero (INV-022: 122,142 payload bytes, 0 nonzero) and nothing in the 132-byte
prefix matches Block3's length, Block1's word count, or the strip count — the first five words
are `0 0 1 0 0` on the cube's face 0, where those counts are 6, 6 and 1. No cross-reference to
the zero block was found in the adjacent record.

The caution from INV-022 stands: constant data supports no semantic inference, and that now
extends to its linkage — an absence of references is not evidence that none exists elsewhere in
the file.
