# EXP-082 — Production parts (in progress)

The controlled set reads byte-exact (EXP-079 to EXP-081). This experiment runs the same readers on the
real parts in `test files original/`, which span many SolidWorks releases. The version of each file
comes from its History stream (the SolidWorks version numbers it was saved with):

| file | versions in History | feature stream | Config-0 |
|---|---|---|---|
| cube.SLDPRT | 15000 | reads to the end | in progress |
| Helical Bevel Gear.SLDPRT | 15000 | reads to the end | in progress |
| Pocket Wheel.SLDPRT | 16000 | | |
| distributor main boss rev a.SLDPRT | 17000 | | |
| Dekor.SLDPRT | 14000 | | |
| USB hub case TOP / BOTTOM.SLDPRT | 13000 | | |
| PTC GE8080-8.SLDPRT | 12000, 14000, 17000 | | |
| SW2000-s01.SLDPRT | 1500 | no ResolvedFeatures stream (pre-2011 layout: the feature tree lives in Config-0) | |
| chainwheel.sldprt, plate4.sldprt | none found | older container, no ResolvedFeatures | |

"Reads to the end" means `probe.js` reads `Config-0-ResolvedFeatures` from byte 0 to the last two bytes,
which are zero, as they are in 23 of the 49 controlled models. After every change below, all 49 controlled
models (24 SW2022, 25 SW2011) still read to the end, and the other real parts stop exactly where they did
before.

## New layouts found so far

From cube.SLDPRT (a SW2022 part made by hand, with sketch dimensions):

- **Sketch dimensions.** The 38 bytes after a sketch's arcs, empty in every controlled model, are 32
  bytes of further (still empty) entity lists, a u16 count with that many dimension objects, and 4
  bytes. A point-to-point dimension (sgPntPntDist) is u32, the value (moLengthParameter_c: the short
  node "D1" and the value in metres, 0.04), 3 bytes, u32 the dimension's sketch id, 16 bytes, u32 1,
  u16 2 (entities), u16 1, u32, the two point handles, three u16 1, 28 bytes. (The gear splits this
  further, see below: the last 2 of the 32 bytes are a count of their own, and so are the 4 bytes.)
- **Profile tail.** After i32, u32, u32 (101 Origin, 102 sketch) comes u32, then u16 n and n objects
  (one in cube.SLDPRT), then 6 bytes (2 in SW2011). Every controlled model had n = 0, which is why
  this used to read as 12 fixed bytes. (The gear shows the 6 bytes are another count and a u32, see
  below.)
- **moSimpleSurfIdRep_c**, a face named by its feature alone: context, moFR_c, u32. In cube.SLDPRT it is
  the profile object above.

### Helical Bevel Gear.SLDPRT

A third-party part, not covered by this repo's license (see NOTICE). Its feature stream is 181,543 bytes and
holds Front, Top and Right Plane, Origin, Sketch1, Revolve1, Sketch2, Plane1, Sketch4, Plane3, Sketch7,
Loft2, Sketch9, Boss-Extrude3, Chamfer2, CirPattern1, Sketch10, Cut-Extrude1 and Chamfer3, plus the usual
folders. It's the first file here with sketch patterns, offsets, a loft with three profiles, a circular
feature pattern and a cut through patterned faces, so most of what follows is new.

**Sketches**

- **The block after the arcs** is 30 bytes of still-empty lists, then four u16-counted lists of
  dimensions: diameters (sgCircleDim), distances (sgPntPntDist and the others below), one list that is
  empty everywhere so far, and offsets (sgOffsetDim). The diameter count was the last two bytes of the
  old 32, and the third and fourth counts were the old 4 bytes.
- **Relations** come in three lists, by how many entities they tie: one, two, three. The three-entity
  list (Sketch2: a symmetric relation, type 11, two points and a line) ends each relation with 6 bytes.
  Its count was the first u16 of the 12 bytes that used to follow the relations.
- **The rest of those 12 bytes**: three u16, a u16 count of circular sketch patterns, and a two-entity
  relation list whose items have 20 more bytes each (the relations that tie the pattern's copies).
- **A circular sketch pattern** (Sketch2, 8 copies): u32 23, u32 24, u32 1, 6 bytes, u16 8, u16 8,
  24 bytes, a line handle, 4 bytes, a line handle, 6 bytes, an arc handle, 8 bytes, the centre point's
  handle, u32 1, u16, the count dimension. Fields are named by position.
- **Arcs and lines** are told apart by the list they're in, not by their type field. Sketch2 has arcs
  of type -1, and lines come with types 0, 0x10000 and 0x20000.
- **Sketch on a face**: after u32 4, 16, 1 comes the count of edge indices. The reader took the count
  from the u32 before; C18 has 4 of both so it never showed. The gear's Sketch2 has 1.
- **Placement of a sketch on a face**: u32, u8 has-rotation and the 3×3 rotation when set (Sketch9),
  the offset along the normal as a vector, f64 scale, u8, u32 1, 23 bytes, f64 1.0, u8, u32 4.

**Sketch dimensions**

- **sgPntLineDist, sgLLDist, sgPntPntHorDist, sgCircleDim** share sgPntPntDist's layout, with line
  handles where the dimension measures a line. A diameter has u32 15 in place of 1, and its handles
  are the circle's arc handle and an **sgEntHandle**: u32 0xfffe777f, i32 -1, u32 0xffff (12 bytes,
  where the point, line and arc handles have 10).
- **sgOffsetDim** (Sketch4: 32 arcs offset from 32 others): u32, the distance (moLengthParameter_c),
  3 bytes, u32 sketch id, 16 bytes, u32 16, u16 2, u16 1, u32, u16, u16 1. The sketch's two-entity
  relations then hold one relation of type 16 for each source and offset pair.
- **sgCircularPattCntDim**: u32, the count (**moIntegerParameter_c**: the short node, then u32), 3 bytes,
  u32 sketch id, 16 bytes, u32, u16 2, u16, u32, two empty handle slots.

**Displayed dimensions**

- **The view list.** Every display dimension's settings hold, at offset 151, u32 n and n annotation
  view numbers (from 200). Every controlled model has one view. Two of CirPattern1's dimensions have
  none, so their records are 4 bytes shorter.
- **moDisplayRevolveDim_c**: the common layout, then 246 bytes (f64 -1 at 128, 1.0 at 152, then what
  look like two directions and a point; not split yet).
- **moDisplayCircularPattCntDim_c** and **moDisplayDim_c** are the common layout with nothing after it.
- **moDisplayRadialDim_c** on a sketch radius has no edge after its 124 bytes.
- **moSkDimHandleValG2_c**, and the same layout for moSkDimHandleRadial_c and
  moSkDimHandleCircularPattCnt_c: 103 bytes (63 in SW2011), then the sketch.

**Profiles**

- **The profile tail's 6 bytes** are a u16 count of edges and a u32 (just the count in SW2011).
  Sketch9 has four edges, each named by a trimmed segment: **moSegmRightTrimEdgeIdRep_c** and
  moSegmLeftTrimEdgeIdRep_c are context, moFR_c, u32 sketch entity, u32.
- **Profile types 103 and 109** (Sketch2, Sketch4) have u16 18, a **moContourChooser_c** and 6 bytes in
  place of the u32 and the lists. 102 and 104 (Sketch9) have the lists. The rule is fitted as "odd
  types above 101". moContourChooser_c is u16 0, u32 1, u32 the owning profile feature's archive index,
  14 bytes.

**Features**

- **The body header's scope**: per body, u16, the body, then u32 k and k kinds, then the creating
  feature's id, u32, u32. The controlled cuts have one kind (101), so this read as five fixed u32.
  Boss-Extrude3 has 103, 101 and Cut-Extrude1 has 107, 106, 103, 101.
- **The 16 zero bytes after the owner** in extrusions, revolves, lofts and split lines are u32 n,
  u16, u16, n groups (a chooser, u16, u16, a bounding box, u16), u32, u32. Revolve1 has one group.
  The face references in a group's chooser list their reps as chains: one null-terminated list per
  rep with its children flattened, ended by an empty list.
- **moPMarkRecord_c** (SW2022): 44 bytes, u32 n, n × (u32 kind, string), 14 bytes. n is 0 in every
  controlled model; Revolve1 has one entry, kind 101 with a GUID.
- **moBBoxCenterData_c** in Cut-Extrude1 has a GUID string and 6 bytes before its owner, and nothing
  before them counts them. The reader peeks for the FF FE FF that starts a Unicode CString (as a tag it
  would be a new object of class 32511, so it can't be mistaken for a real owner).
- **moPerBodyChooserDataWithFileName_c** (Cut-Extrude1) is written as the plain chooser: there's no
  file name in it here.
- **moFaceRefPlnData_c** for a plane offset from a face (moCompFace_c, as in C18 and Plane1) has no
  handle slot and 56 bytes after the reference (40 in SW2011).
- **moLineRef_w** on a model edge (CirPattern1's axis) has u32, u16 after the edge, like
  moSketchExtRef_w.
- **moBlend_c** (loft): after the profiles comes u32 0, u32, one u32 per profile, one per neighbouring
  pair, a point per profile (Loft2: its profiles' planes at z 0, 0.05, 0.1), one u32 per profile, then
  settings of fixed size. C16 has 2 profiles and fit the old fixed layout by chance.
- **moArcBackedUpData_c** (Sketch9): the end points as a linked pair, the centre point, 7 bytes, the
  name ("Edge").
- **moCirPattern_c** (CirPattern1, 13 copies over 360°): the body header, 18 bytes, u32, the feature
  data, the patterned features (an object list: Boss-Extrude3), an empty list, 11 bytes, an empty list,
  228 bytes of settings, an empty list, 11 bytes, four dimension slots (the count shown, null, the count
  and the angle hidden), u16, the axis, u8, the angle shown, u32 1, u8, u32 1, 7 bytes.
  **moNumberDim_c** (the count 13) is u32, then the value.

**Face and edge naming**

- **moSurfaceIdRep_c** (applied features) has as many reps as the feature's n − 1 (one in the
  controlled fillets and chamfer, two in Chamfer2), then u16 n and n edges. The edge count used to read
  as a reference to object 1.
- **moCirPatternSurfIdRep2_c**, a face of one pattern copy (Cut-Extrude1): context, moFR_c pointing at
  CirPattern1, the seed face's rep. When that rep is a moFromSktEnt3IntSurfIdRep_c it has two more u32
  after its three ints (12, 0 and 11, 0 here, the same number as the sketch entity of the rep under it).
  The cut's faces name copies 12 and 11.
- **moSimpleSurfIdRep_c** with a null context (Cut-Extrude1's faces and Chamfer3's edges, where its u32
  is 1) has a child rep, as moPLineSurfIdRep_c has extra slots when its context is null. In a profile
  (context set, u32 0, cube.SLDPRT and Sketch9) it doesn't.

### Controlled layouts this corrects

None of these changed what the controlled models read, because the counts are 0 or 1 there. They're
real counts now, not fixed bytes:

| was | is |
|---|---|
| 32 + 4 bytes around the sketch dimensions | 30 bytes, then four counted dimension lists |
| 12 bytes after the relations | the three-entity relations, three u16, the sketch patterns, the pattern relations |
| profile tail, 6 bytes (2 in SW2011) | u16 edge count and u32 (count only in SW2011) |
| five u32 per scope body | u16, body, u32 k, k kinds, three u32 |
| 16 bytes after an owner | u32 group count and the groups |
| moPMarkRecord_c, 62 bytes | 44 bytes, counted (kind, string) entries, 14 bytes |
| display dimension settings, fixed size | a counted view list at offset 151 |
| moSurfaceIdRep_c, three objects | n − 1 reps, u16 edge count, the edges |
| moBlend_c, five u32 and six doubles | per-profile and per-pair lists |
| sketch on a face, count read first | three u32, then the count |

### Fitted on this one file

These match the gear byte for byte but rest on a single example, so they may not hold elsewhere: the
odd-type rule for profile choosers, the whole of moCirPattern_c, the chained reps in extra groups, the
peek for the bounding box GUID, the two extra u32 under a pattern rep, and the null-context rule for
moSimpleSurfIdRep_c. moDisplayRevolveDim_c's 246 bytes aren't split yet.

### How the misses showed up

The worst bug on the way was a whole object read as part of another. An sgLineHandle (Sketch2's
revolve axis) went into the edge index list because the count came from the wrong u32. Nothing failed
at that point; the stream kept reading, and only later did a class index come out one short of what
the writer used (946 for 947). Because classes and objects share one index sequence, any object the
reader swallows shifts every later reference. So a reader that gets to the end is the check that
matters, and every layout above was kept only if all 49 controlled models still got there too.
