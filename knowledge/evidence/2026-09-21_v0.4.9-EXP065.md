# EXP-065 — NQ-047: C04 is not the outlier, and the question had the wrong premise

Date: 2026-09-21. Base: staging `e45775f`.
Scripts: `scripts/EXP065/`. Reproduce:

```sh
node knowledge/evidence/scripts/EXP065/what-does-Z-count.js    # candidate counts, all scored
node knowledge/evidence/scripts/EXP065/z-as-id-ceiling.js      # ID-ceiling reading, falsified
node knowledge/evidence/scripts/EXP065/z-vs-feature-tree.js    # grouping test (see §5: inconclusive)
```

NQ-047 asked why `C04_cube_hole_5mm` reads 316 where `C05`/`C06`/`C11` read 293. **It does not
have an anomalous value. It has a different model.** The premise that the four are four builds of
one thing is false, and it was our premise, introduced in EXP-064.

---

## 1. The field is not a probe artefact and not a byte count

First the boring possibilities, closed:

- The `Z 00 02` marker occurs **exactly once** in each file, at offset 961 in all four SW2022
  models and 824 in all four SW2011 models. 316 vs 293 is a real difference at the same field,
  not my probe landing somewhere else.
- All four SW2022 transmits are **exactly 7,364 bytes**; all four SW2011 transmits are exactly
  5,829. A field that differs by 23 across identical-length files is not counting bytes.
- The text forms have **identical integer counts** (1,993 in all four), and C04 has one *fewer*
  record introducer (16 vs 17). The field is *larger* where there is *less* content, so it is not
  counting content present in the transmit.

## 2. The models differ in feature history

Reading the UTF-16LE feature names out of the SLDPRT streams:

| model | feature tree | SW2022 Z (text) |
|---|---|---|
| `C04_cube_hole_5mm` | `Sketch1, Boss-Extrude1, Sketch2, **Cut-Extrude1**` | **309** |
| `C05_cube_hole_3mm` | `Sketch1, Boss-Extrude1, Sketch2, **Cut-Extrude2**` | 286 |
| `C06_cube_hole_moved` | `Sketch1, Boss-Extrude1, Sketch2, **Cut-Extrude2**` | 286 |
| `C11_cube_hole_4mm` | `Sketch1, Boss-Extrude1, Sketch2, **Cut-Extrude2**` | 286 |

SolidWorks names a feature from a monotonic per-type counter. A tree whose *only* cut is called
`Cut-Extrude2` is a tree in which a `Cut-Extrude1` existed and was deleted. So C05, C06 and C11
each carry a removed feature in their history; C04 does not.

The split in Z lines up exactly with the split in provenance — and it is C04 that is built the
ordinary way, three-to-one against it only because the other three share an edit history.

**The 2011 corpus is the control.** There, all four models are `Cut-Extrude1` — clean builds —
and all four read **297**:

| | feature tree | Z |
|---|---|---|
| SW2011 C04, C05, C06, C11 | all `Cut-Extrude1` | all **297** |
| SW2022 C04 | `Cut-Extrude1` | 309 |
| SW2022 C05, C06, C11 | `Cut-Extrude2` | 286 |

Same topology throughout. Where history matches, Z matches; where history differs, Z differs.
The build log confirms identical volume (`803.650459` mm³) for C04 and C06, so the difference is
not geometric.

Supporting detail: C04's transmit header carries `DATE=Mon Sep 21 08:03:10`, against 07:58–07:59
for the other three — a separate export run, consistent with a separately built model.

## 3. So NQ-047 dissolves, and NQ-043's evidence has to be re-read

EXP-060 concluded "the field is not a topology count" from C04 vs C06 alone. EXP-064 corrected
the comparison but kept the assumption, calling C04 unexplained. Both readings rest on treating
the four as interchangeable. They are not.

What the corpus actually supports: **Z depends on topology *and* on feature history.** Identical
topology with identical history gives identical Z (SW2011, 4/4; SW2022 C05/C06/C11, 3/3).
Identical topology with different history gives different Z (C04 against those three).

The `Z` field therefore cannot be a pure count of the body's topology, but the reason is
provenance sensitivity, not the position-sensitivity EXP-060 claimed — moving a hole does not
change it, as C05/C06/C11 (differing in both hole size and position) all reading 286 shows.

## 4. The "ID ceiling" reading is falsified

The obvious candidate for a history-sensitive, content-insensitive number is an allocation
high-water mark: IDs ever handed out, including those freed by deleted features. It predicts node
IDs running 1..Z with gaps.

It fails on the full corpus. `C15_torus` has a dense integer prefix of **57** against Z = **44**,
and `C16_loft_spline` has 369 against 355 — IDs above the supposed ceiling. Six SW2011 and ten
SW2022 models carry ID-like integers above Z.

Every structural candidate scored against both corpora — total integers, distinct integers, max
integer, record introducers, max record id, named attribute records, body length — matched
**0/24 and 0/25**, with no constant offset. Recorded because "no candidate fits" is the useful
result: whatever Z counts is not visible in the text transmit's surface structure, so decoding it
needs the node record grammar, not another correlation.

## 5. Where this experiment's own test failed

`z-vs-feature-tree.js` was meant to score topology grouping against feature-tree grouping across
the whole corpus. **Both signatures are too coarse and the test is inconclusive** — reported
rather than quietly dropped:

- The topology signature (face count + sorted surface tags) cannot separate a cube with a hole
  from a cube with a fillet: both are six planes and one cylinder.
- The feature-tree signature de-duplicates names, so `C05` (one hole) and `C07` (two holes in one
  sketch) produce identical signatures.

It reports 0/4 consistent groups in both groupings, which measures the signatures, not the
hypothesis. The §2 result does not depend on it: that is a direct reading of four models'
feature trees against their Z values, with the 2011 corpus as control.

## 6. Correction to EXP-064's language: none of it is noise

EXP-064 described 978,357 scan hits as "denormal garbage". That was wrong as a description, and
the wrongness matters because reading those bytes back is the project.

Those offsets hold **small integers** — counts, indices and array headers — read at 8-byte width.
At `C00`'s first face the three values are `1.68e-44`, `1.40e-43`, `2.80e-45` as `f32`, which are
int32 **12, 100, 2**: the `[12, 100, 2, V]` positions header we already document. Reading any two
adjacent small integers as one `f64` yields a value near 1e-312, and two such values trivially
satisfy a 1e-12 absolute test.

**52.8%** of all byte offsets in `C00`'s DisplayLists decode as tiny-nonzero `f64`, because the
stream is mostly integer data. The radius floor was still the right fix, but the reason is that
those regions are integers rather than floats — a fact about the format — not that they are
noise. The corrected reading is in INV-026's note.

|---|---|
| C04 has an anomalous Z value | **premise withdrawn** — different feature tree (`Cut-Extrude1` vs `Cut-Extrude2`) |
