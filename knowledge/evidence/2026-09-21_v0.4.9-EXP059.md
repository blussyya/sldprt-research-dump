# EXP-059 — Adversarial review of EXP-058 and EXP-056

Date: 2026-09-21.
Base: staging `fd838f1`.
Scripts: `scripts/EXP059/`. Reproduce with `node knowledge/evidence/scripts/EXP059/review.js`.

EXP-058 corrected two claims in EXP-056. Both corrections are **upheld**. Reviewing them
surfaced a defect affecting *both* experiments' headline numbers, and three further limits.

---

## 1. EXP-058's corrections to EXP-056 are correct

### 1.1 "19 entries" was wrong — the prefix is 13

EXP-056 reported that its binary reader stopped at 7 entries "where the text form continues to
19", implying 19 was one table. It is not. Positions of the 19 matches in `C00_cube_10mm`'s
`.x_t`:

| transition | gap (chars) |
|---|---|
| within the first 13 | 13–30 |
| `mesh_offset_data` → `list_type` | **148** |
| `finger_block` → `owner` | **203** |
| `owner` → `index_map_offset` | **4,572** |

The last match sits 5,442 characters into the stream, inside node data. `readTextSchemaTable`
uses a global regex over the whole transmit, so it reported scattered later declarations as
members of the initial table. The contiguous prefix is **13**, matching EXP-058's binary count.

EXP-056's own reader stopped at 7 because `index_map_offset` carries a length-prefixed
extension it did not consume. Both numbers in that sentence were wrong.

### 1.2 The flag was never cross-validated

`parasolid/v0.1/test/validate.js` compares only `name` and `code`, and loops to
`Math.min(bin.length, text.length)`. It therefore **cannot** detect a flag mismatch or a length
disagreement. "24/24 schema tables agreeing" describes a narrower check than it sounds like.

## 2. The headline counts overstate independence — affects both experiments

| measure | result |
|---|---|
| distinct export declaration tables across the 24 SW2022 models | **1** |
| distinct raw byte sequences for export bytes 0–349 | **1** |
| distinct partition declaration tables across the same 24 | **1** |

Bytes 0–349 are **byte-identical in all 24 models**. So:

- EXP-058's "24/24 agree, 312 declarations, boundary 349 in all 24" is one 349-byte sequence
  parsed 24 times. 312 = 13 × 24 identical copies.
- EXP-056's "24/24 schema tables agreeing, 168 entries compared" has the same defect.

Both are **n = 1**, not n = 24. The models differ in geometry; the declaration prefix is a fixed
preamble emitted by one SolidWorks build and never reaches the geometry.

**This is not a reason to distrust the readings** — they are consistent and reproducible. It is a
reason to stop reporting replication counts that measure nothing. Corpus diversity must be
asserted on the axis a claim depends on, not the axis that happens to be large.

## 3. The flag cannot be resolved on this corpus at all

EXP-058 records the discrepancy — binary word `1`, text `0` — as uninterpreted. Correct call.

An alternative alignment (flag as `u8` at code+2, followed by a separate always-`1` byte) gives
**312/312 agreement** with the text. That looks like a resolution and is not one:

```
text flag values across all 312 entries : {"0": 312}
byte at code+2                          : {"0": 312}
byte at code+3                          : {"1": 312}
```

Every text flag is zero and every candidate byte is zero, so **any always-zero field agrees**.
The test has no discriminating power in either direction — the same defect this project
identified in an outside project's "finite f32" reading of Block1 (EXP-057 Q2), reproduced here
in the opposite direction.

Both alignments remain live. Settling this needs a file whose flag is nonzero; none exists in
any corpus we hold.

## 4. The reader generalizes further than claimed — but its constants do not

EXP-058 tested only the 24 SW2022 exports. Run wider, `binary()` holds up well:

| source | files | parsed | failed |
|---|---|---|---|
| SW2022 exports | 24 | 24 | 0 |
| SW2011 exports | 25 | 25 | 0 |
| original-corpus partitions | 21 | 21 | 0 |

That is real generalization across genuinely different inputs, and it is stronger evidence than
the 24× replication. But the numbers EXP-058 reports as constant are **version-dependent**:

| schema | entries | Z at byte |
|---|---|---|
| `SCH_2201236_20000_13006` (SW2011 exports) | **4** | **204** |
| `SCH_3201230_32001_13006` | 7 | 244 |
| `SCH_3101290_31100_13006` | 7 | 244 |
| `SCH_3301247_33103_13006` | 8 (partition) / 13 (export) | 257 / 349 |
| `SCH_3401247_34101_13006` | 8 | 257 |
| `SCH_3501251_35102_13006` | 8 | 257 |

"13 entries", "8 in partitions" and "byte 349" describe one modeller version, not the format.
The original corpus alone yields **5 distinct partition prefixes**.

## 5. `textPrefix()` is schema-locked

It asserts a hardcoded text preamble `/^230 0 \d+ \d+ /`. SW2011 writes `186 0 12 27`.

```
SW2011 exports:  binary() parsed 25, failed 0
                 textPrefix() parsed 0, failed 25   ("unknown text preamble")
```

The cross-validation half of the experiment — the part that makes the binary read trustworthy —
works on exactly one schema. Filed as NQ-041.

## 6. The extension rule is fitted to two names

Only two names ever carry code 0: `index_map_offset` and `lowest_node_id`. Every observed
extension, across all corpora, is the one-byte string `"d"`. The length prefix has **never** been
observed at a length other than 1, so the "length-prefixed extension string" mechanism is
untested as a mechanism, and `code === 0` cannot be distinguished from "these two names" as the
real trigger.

EXP-058's corruption control flips that single byte. It proves bytes are copied faithfully; it
cannot test a length-prefix grammar that never varies.

## 7. Unclaimed finding: the value after `Z` tracks model complexity

Bytes at the boundary, `u16be` at `Z + 5`:

| model | value | faces |
|---|---|---|
| `C14_sphere` | 68 | 1 |
| `C00_cube_10mm` | 232 | 6 |
| `C20_cylinders_crossed` | 297 | 8 |
| `C16_loft_spline` | 361 | 6, four of them B-surfaces |

Constant across all 24 within a model set, varying between models in rough proportion to
complexity. This is the most promising lead for the next step: a plausible **node count**, which
is exactly what NQ-037's next milestone needs, and it is checkable — a cube's node total is
predictable from 6 faces, 12 edges, 8 vertices.

Not claimed as decoded. It is a lead with a number attached.

(First measured at `Z + 1` during this review, which gave a constant and looked like a refutation
of the reviewer's report. The offset was wrong; the value sits at `Z + 5`. Recorded because the
near-miss argues for reading bytes rather than trusting a single probe.)
