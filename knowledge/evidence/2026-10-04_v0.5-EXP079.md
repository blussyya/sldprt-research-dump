## Part A. How SolidWorks writes what STEP can't express

EXP-078 wrote intersection curves and rolling-ball blends as B-splines, because STEP has no exact
form for either. Question: what does SolidWorks' own STEP export do with them, and should ours
follow it?

The only real parts in the corpus with a SolidWorks STEP are the two USB hub halves. They are the
same model as the SLDPRT: all 82 (TOP) and all native vertices of BOTTOM coincide with STEP
vertices to 3.5e-18 m; the extra STEP vertices are seam splits.

| | SolidWorks' STEP | ours (EXP-078) | ours (now) |
|---|---|---|---|
| declared uncertainty | 1e-5 mm (10 nm) | 1e-8 × unit | same |
| intersection / tolerant edge curves | cubic B-splines, knot multiplicities 4, 2, …, 2, 4; worst 0.98 µm (TOP), 0.86 µm (BOTTOM) from the true curve | cubic, multiplicity 3, within 1e-9 m | multiplicity 2, same curves (removing the redundant point moves the curve by 4.5e-16 m) |
| curve control points (TOP, 22 curves) | 208 | | 1,540 |
| B_SURFACE faces | copied (rational 2×3, 3×10) | copied | copied |
| rolling-ball blend (TOP, 1 face) | rational B-spline, degree 3 along the spine × 2 across, 10 × 3 points; about 1.5e-7 m off | bicubic, 33 × 25 points, within 1e-8 m | rational, degree 3 × 2, 17 × 3 points, within 1.5e-9 m |
| volume vs the exact body | +0.0205 mm³ (TOP), +0.0190 mm³ (BOTTOM) | exact | exact |
| file size | 241 KB (TOP), 142 KB (BOTTOM) | | 177 KB, 84 KB |

So SolidWorks approximates exactly where we do, at about 1 µm on curves and 0.15 µm on blends, and
its own STEP is not the exact body (its volume is off by 2–3 parts per million).

One choice of SolidWorks' is better than ours was: across a blend it writes a **rational quadratic**,
which is the exact circular arc, and approximates only along the spine. The package now does the
same (`blendSurfaceRational` in `src/brep/blend.js`): exact cross-sections interpolated in
homogeneous coordinates along the spine, with sections added until the surface is within 1e-8 m of
the blend. A point is on the exact blend when it is |range| from the spine (the envelope of the
rolling ball) and the two boundary rows lie on the supports; that is what is checked.

| part | blend faces | form | worst deviation | control points per face | before |
|---|---|---|---|---|---|
| USB hub TOP | 1 | rational arc × cubic | 1.5e-9 m | 51 | 825 |
| Pocket Wheel | 32 | rational arc × cubic | 8.7e-9 m | 99 | about 1,900 |

Checks after the change: both parts round-trip; OpenCascade reads TOP, Pocket Wheel, chainwheel and
Dekor as one valid solid each; our volumes are unchanged to 3e-10 relative and OpenCascade's
analytic volume of Pocket Wheel now agrees with ours to 1.5e-9 (was 2e-9).

## Part B. The feature tree stream (in progress)

Notes kept as the reader is built; to be completed.

- The tree is in `Config-N-ResolvedFeatures` (modern and SW2011). It is an MFC `CArchive` object
  stream: `FFFF` + schema + name for a new class, `0x8000 | k` for a new object of class k, plain
  `k` for an object already read. Classes and objects share one index sequence.
- Modern files: the stream starts u32 N, u16 M. M is the number of top-level objects (19 in C00).
  The index sequence starts at **N itself**. An earlier note here said N + 3; that came from
  missing three nested objects (see the next point). Indices below N belong to classes and objects
  of an earlier archive in the file (Config-0's). SW2011 files start with u16 M directly.
- Words `0x8000 | k` with k below N are **new objects of pre-loaded classes**, written inline, and
  each takes an index. Three occur everywhere: k = 4 at the start of every feature (the node-name
  object: name, flags, id, comment, children, order, version stamps, display state), k = 43 at the
  start of every `moComp*` object, and k = 82/83 inside point handles. Their k varies per file
  (the point class is 0x52, 0x53, 0x98 or 0xb1), so the reader finds them by role. With this rule
  every anchor in C00 lands exactly: HFID 118, moCompFeature_c 120, the second notes folder 138,
  moRefPlane_c 158, moDefaultRefPlnData_c 161.
- The node object's children are objects: back-references (Boss-Extrude1's sketch) or whole child
  features (the Annotations folder's two notes folders).
- `swXmlContents/KeyWords` (modern) is a plain XML index of the tree: every feature's id, name and
  type, and some dimension values (C04: Boss-Extrude1, D1 = 10).
- Every feature object starts with a nested object of class #4 (modern) holding the name (UTF-16
  MFC string), flags, the feature id (equal to the KeyWords id on every feature checked: planes
  2/3/4, Origin 5, Sketch1 26, Boss-Extrude1 32, Sketch2 33, Cut-Extrude1 46), a comment, a list
  of object references (an extrude's references include its sketch), an order number, created and
  modified version/build stamps (15000 / 2022009) and a FILETIME.
- About 160 classes occur in the stream across the corpus; the controlled models use about 60.

### Sketches: decoded on every SW2022 controlled model (2026-10-04, later)

[`sketch-scan.js`](scripts/EXP079/sketch-scan.js) reads sketch geometry by record signature; its
output for all 23 native SW2022 models is [SKETCHES_SW2022.txt](scripts/EXP079/SKETCHES_SW2022.txt).
Every sketch matches the part as built: the 10 and 20 mm squares, C02's square moved to (50, 50),
the hole circles with radius 2.5, 1.5, 2.0 mm at their centres (C06 moved to (7, 5); C07/C08 two
holes, the second resized to 1.5 mm), C13's 5 × 10 triangle, C14's radius-5 semicircle, C15/C17's
radius-2 circle at (5, 0), C16's centred 10 mm square with diagonals and radius-4 circle, C18's
split line at y = 5, C19's semicircle, C20/C21's radius-5 circles.

Grammar (SW2022):

| part | layout |
|---|---|
| sgSketch | u16 point count (including point 0), 12 bytes; then point 0, which is the first point drawn (the rectangle's corner, a circle's centre) |
| attribute block | `FF FF 1F 00 03 FF×8`, f32 −1, …; 35 bytes, one object field (null, or an external reference such as the Origin), 27 bytes |
| point | u32 id, attribute block, u16 kind (0x1e/0x1f), f64 x, f64 y, u16; then the handles of the entities that end there (u16 count + handle objects) and 48 bytes. A point tied to outside geometry carries the reference chain sgExtEnt_c → moSketchExtRef_w → moCompSketchEntHandle_c (component object, point handle 0 = the Origin's point, 58 bytes) → moPointBackedUpData_c (32 bytes + its name, "Point1@Origin"), and has no handle list |
| line/arc handle | sgLineHandle / sgArcHandle: u16 entity id, i32 −1, u32 0 |
| segment | attribute block, u16 start, u16 end, u16 a, u16 b, f64 −1.0, u32 type (0 line, 1 arc), for arcs u16 centre; a = 0 marks construction geometry (revolve axes, rectangle diagonals) |
| indices | start/end/centre index the sketch's point list in order, 0 = point 0 |
| relations | u32 type, u32 2, …, handles of the entities. Types seen match SolidWorks' API enum `swConstraintType_e`: 4 horizontal, 5 vertical, 9 coincident, 14 equal length |

Only point records hold coordinates: C00 and C01 (10 and 20 mm cubes) differ in exactly three
places in the whole sketch, the three non-zero coordinates.

### Feature list and dimensions: `swXmlContents/KeyWords`

Modern files carry a plain XML index with every feature's id (= node id in the stream), name,
type and dimension values in display units: `Boss-Extrude1 {D1=10}`, `Fillet1 {D1=R1}`,
`Chamfer1 {D1=1, D2=45°}`, `Shell1 {D1=1}`, `Revolve1 {D1=360°}` (C17: 90°), C20's two-direction
extrudes `{D1=10, D2=10}`; Cut-Extrude (through all), Loft and Split Line list none. In the
archive, a dimension is a `moLengthParameter_c` / `moAngleParameter_c`: the short node form (name,
id −1, comment, u16) followed by the value as f64 in metres or radians (C00 D1 = 0.01).

Next: the sketch plane reference (moCompRefPlane_c in each moProfileFeature_c), extrude end
conditions and direction (moEndSpec_c, moFromEndSpec_c), and how fillets, chamfers and shells
name their edges and faces (moEdgeRef_c / moFaceRef_c and the *SurfIdRep classes).

### The sequential reader (2026-10-04, night)

`probe.js` now reads the stream strictly: exactly M top-level slots (the last one is a null on
every file so far), nothing skipped, every object index checked by the references that follow.
Files read from the first byte to the last: **C00, C01, C02, C03, C12, C19, C24** (cubes, the
fillet models, the half cylinder). The rest stop at a feature class without a reader yet (cut,
revolve, chamfer, shell, loft, split line) or, for C23, at the SW2011-upgraded layout.

Corrections to the notes above:

- The feature node ends six bytes after the `02 00 7c 09 05 00 01 00` stamp, not ten. The
  Annotations folder proves it: its own two doubles (1.0, 1.0) start right there. Every class
  reader gained the four bytes.
- The component object (`2b 80`, pre-loaded) is 79 bytes for every owner. The feature id and its
  creation time (unix seconds, e.g. 0x6ab0b4f1 = 2026-09-21 for Sketch1 of C00) belong to the
  owning class (moCompFeature_c, moCompRefPlane_c, moCompSketchEntHandle_c). Faces, edges and
  bodies (moCompFace_c, moCompEdge_c, moCompSolidBody_c) add a byte and a face or edge reference
  instead.
- Index 1 is never defined in any stream: it is the document, mapped in advance (MFC
  `MapObject`), and `01 00` where an object is expected is a reference to it.
- The pre-loaded class read as "point" is an object list (count + objects), probably `suObList`
  from Config-0's archive.

Sketch object (sgSketch), SW2022, in order:

| part | layout |
|---|---|
| points | u16 count, u16, then per point: u16 (1 when tied to outside geometry), u32, u32 id, attribute block, u16 kind, f64 x, f64 y, u16 flags (2 = start of a full circle, 1 the Origin's point, 8 split-line points), u16 number of entities using it, two handle slots, u16 number of arcs centred on it, i32 −2, 36 bytes |
| lines | u16 count, u32, then per line: u32 order, i32 id (−1 for the rectangle's construction diagonal), attribute block, u16 start, u16 end, u16 a (0 construction), u16 b, f64 −1, u32 type |
| arcs | 6 bytes, u16 count, u32, per arc as a line plus u16 centre, four i32 −2 and a u16 |
| other entity lists | 38 bytes, empty in every controlled model |
| relations | one list per entity count: u16 count, then per relation 8 bytes, i32 −1, 16 bytes, u32 type (swConstraintType_e), u32 2, u16 0, i16 −2, u16 0, the handles; two-entity relations add 8 bytes, two i32 −1, 24 bytes. Then 12 bytes |
| object list, 12 bytes, u16 ×2 | |
| next ids | 14 × u32: the next free id per entity kind (C00 Sketch1: 5 orders, 6 points, 5 lines, 1 arc, …) |
| misc | 4 × u32, a string, u16, f32 −1, i32 −1, u32, i32 −1, 24 bytes, 2 × u32, 28 bytes |
| regions | object list of moSketchRegion_c, each holding an object list of the boundary's handles |
| chains | 30 bytes, u32 count, u32, per chain a moSketchChain_c (u16 n, the entities' order numbers, u16, u32, u32 6, i32 −1, 8 bytes) and 38 bytes |
| tail | u32 3, u32 1, 7 bytes, u32 100000, u16, the revolve axis handle (null unless a centreline is used) |
| plane | moCompRefPlane_c: the plane feature by id and time, u16, u32 (3, or 2 with a rotation), u8 has-rotation, 3×3 rotation (Top: [[1,0,0],[0,0,1],[0,−1,0]]), 24 bytes, f64 1.0, 3 bytes, u32 4 |

Points tied to the Origin carry sgExtEnt_c → moSketchExtRef_w → { moCompSketchEntHandle_c (the
Origin feature, its point handle, 62 bytes), moPointBackedUpData_c (30 bytes, "Point1@Origin") }.

Extrusion (moExtrusion_c): node; u32, u16, u32; a linked list of (u16 1, u16 code 0x3a/0x3b, u32
more); u16; u32, u32 101 (102 for cuts), u32 3; the bodies it acts on (u32 count, then per body
u16, moCompSolidBody_c, u32 1, u32 101, the creating feature's id, u32 102, u32 90); u32 1, u16,
u16; the body chooser (the result named by its cap faces); u16 ×2; bounding box (centre and
diagonal); u16, u32, a back-reference to itself, 16 bytes, u32; a pre-loaded feature-data object
(66 bytes); the end condition (moEndSpec_c: 24 bytes, the depth dimension, the second direction's
dimension); u8 flag and, when set, 42 bytes; 31 bytes; moFromEndSpec_c (32 bytes).

Faces and edges are named, not stored: moFaceRef_c / moEdgeRef_c hold u32 1, u32 0, u32 kind (6
face, 4 edge), a few small fields, a 64-bit key twice, and a tree of surface-id representations.
Each representation names the feature that made the face (moFR_c: document, feature id, creation
time) and how: moFromSktEntSurfIdRep_c (side face swept from sketch entity N),
moEndFaceSurfIdRep_c (cap face, end 0 or 1), moFilletSurfIdRep_c (face of a fillet). C03's filleted
edge is named by the side faces from sketch lines 3 and 2 and the two caps.

Displayed dimensions (moDisplayDistanceDim_c, moDisplayRadialDim_c): 556 bytes of annotation
settings; moFeatureDimHandle_c (103 bytes) holding the dimension object (ParallelPlaneDistanceDim_c,
ThreeDRadiusDim_c: u32, the parameter: short node "D1" + f64 value); placement data whose length
depends on the measured geometry (587 bytes for the cube extrusions, 515 for the cylinders, 541 for
fillet radii); moFavoriteHandle_c; 374 bytes; a type-specific tail (54 bytes for distances; for
radii 124 bytes and the measured edge). The placement block is the one stretch the reader does not
decode: it goes to the favourites handle that follows, and refuses if a class definition lies in
between, so no object can hide there.

Constant-radius fillet (Fillet_c): node; 58 bytes; feature data object; u32; the filleted edge's
name (moSurfaceIdRep_c → moFilletSurfIdRep_c → moEdgeRef_c); object lists of edges (the edge
component) and three empty ones; 12 bytes; a list of edgeRadiusObject_c, each holding the radius
dimension; u32, u8, an empty list, 8 bytes, 02 02 01 00, 9 bytes, conic rho twice (0.5), …; the
fillet's face and edges as component objects with the radius again (f64); five u32 that look like
Parasolid tags; 16 bytes.

### All 24 SW2022 models read to the end (2026-10-04, late night)

Every file in `test files new/SW2022` now reads strictly from the first byte to the last, including
C23, the cube first saved in SW2011 and re-saved in SW2022. The readers for the remaining feature
classes (cut, revolve, chamfer, shell, loft, split line, sketches on faces) are in `classes.js`,
each with its layout in the comment above it.

C23 differs from the native SW2022 cube in one place. A sketch entity tied to outside geometry
(`moSketchExtRef_w`) is followed by 52 bytes: u16 0, u32 0x66 or 0x6a, 12 bytes, three i32 −12345,
u32 0, **u32 version at offset 34**, 14 bytes. Version 15000 (written by SW2022) is followed by a
backed-up copy object (`moPointBackedUpData_c`). Version 4700 (written by SW2011, and kept when the
file is upgraded) has no object there: only u32, u32 and the entity's name ("Point1@Origin"). The
sketch attribute block of an upgraded file starts `ff ff 07 00 01` instead of `ff ff 1f 00 03`, but
its length and layout are the same.

Layouts added for the rest of the controlled set (SW2022; "bytes" are not yet split into fields):

- **Body header**, shared by extrude, cut, revolve, loft and split line: u32, u16, u32 (split line:
  u32, u32); a list of (u16 1, u16 code 0x3a/0x3b) as one pair, u32 n and n more pairs (cuts add
  0x3b); u16; u32, u32 (101 boss, 102 cut), u32 3; the bodies acted on (u32 count; per body u16,
  the body object, five u32 including the creating feature's id); u32, u16, u16.
- **Cut-extrude** (moICE_c): exactly the extrusion layout. The flag byte after the end condition is
  0 for C19, otherwise 1 followed by u16, u32 1 and 36 bytes; then 19 bytes, u32, 8 bytes and
  moFromEndSpec_c (32 bytes).
- **Bounding box** (moBBoxCenterData_c): u32 1, centre, diagonal, u32, u32, u32 n and n u32 (1 for
  the boss, 0 for the cut), u16, the owning feature.
- **Revolve** (moRevolution_c): as the extrusion up to the feature data object, then u8, u32,
  u32, an object list, u32, u32, the axis (moLineRef_w: the sketch line handle, the 52-byte
  version block, 6 bytes, seven doubles where the first is the line's length, u8), the end
  condition (moRevEndSpec_c: u32 1, 24 bytes, two doubles, 8 bytes, the angle dimension, a second
  one), u32.
- **Angle dimension** (moDisplayAngularDim_c): the common display layout, then u16, three bytes, ten
  doubles (the dimension arc: two directions and points), u32.
- **Chamfer** (Chamfer_c): node, 58 bytes, feature data, u32, the named edge; the edge list, two
  lists, the distance dimension and a second one, u8, u16, u16, the edge component, three u32 and
  a u16, five Parasolid-looking tags, 19 bytes, u8.
- **Shell** (moShell_c): node, 58 bytes, feature data, u32, target; the thickness dimension, u8, two
  lists, the removed face's edge component, u16.
- **Loft** (moBlend_c): body header, owner, 16 bytes, u32, feature data; u32 profile count, u16
  count and the profiles (moGeneralCurveRef_w → moCompProfile_c: the sketch feature by id and time,
  60 bytes; then 4 bytes, f64 1.0, u8, two i32 −1, 6 bytes); a settings block of fixed shape.
- **Split line** (moPLine_c): node, u16 ×2, the projected-curve name (moPLineProjIdRep_c), the body
  header, chooser, bounding box, owner, feature data; u32 n faces split (moPLineSurfIdRep_c), u16 n
  face references, u16 n su_CDWordArray (count + u32 values), u16 n flag bytes, three u16, the new
  face, u16 n + u32 values, i32, i32, u32, the projection (moPLineProject_c: reference, u32, u16 n +
  faces), 8 bytes.
- **Offset plane** (moFaceRefPlnData_c): origin, normal, has-rotation and rotation, a vector, f64
  1.0, u8, a display box of four doubles, 6 bytes, u32, i32, u8, 16 bytes, the reference plane, a
  handle slot, 60 bytes, then the plane again (box, origin, normal, rotation, vector, f64, 25
  bytes), the offset dimension, u32, u32, 8 bytes.
- **Sketch on a face**: after the chains, u32 3 and an on-plane byte. When it is 0 the sketch embeds
  the face it sits on: u32, u8, u32, a 16-byte GUID, the uncompressed size, u32 n and n bytes of
  zlib-compressed Parasolid transmit data, 12 bytes, u16 n and the face's edges, u32 nk, three
  u32, nk edge indices, u32. Its plane is a hidden plane feature written inline (a null node
  pointer, then the node fields without a name) and the placement after it is u16, u32, u8, a
  vector, u8, u32, 23 bytes, f64 scale, u8, u32.
- **Face and edge names**: after the header (u32 1, u32 0, u32 kind, u8, u16, u8, u32 tag, a
  16-byte key, u16), a face carries representations up to a null and an 18-byte tail (16 when
  kind is 1, the sphere's single face); an edge carries one representation and 14 bytes. The tails
  hold the SolidWorks version at offset 6 (15000, or 4700 for objects from SW2011). SW2011 writes 6
  bytes (4 for kind 1) and 2 bytes. The u32 and u16 that follow some edges belong to their owner:
  Fillet_c writes them after its edge, and moSketchExtRef_w after an edge a sketch is tied to. A
  chamfer's edge and a dimension's edge never have them. (An earlier rule, "when the tag is
  non-zero", fitted SW2022 only: SW2011's chamfer edge has a tag and no extra bytes.)
  moPLineSurfIdRep_c has four object slots when its context is null, two otherwise (fitted).

### SW2011 files (2026-10-05)

Files saved by SW2011 have no u32 first-index header: the stream starts with u16 M and the first
class definition. The index sequence still continues Config-0's archive (the feature node class is
pre-loaded at 64 in C00), so the first index has to come from somewhere else. `probe.js` and
`load.js` read once with a provisional index above every pre-loaded class. The first index the reader
can't place must name one of the stream's own classes, so each class gives a candidate, and the
candidate that reads furthest wins: 162 for C00 and C22. Config-0 itself is a complete MFC archive
(moPart_c, moHeader_c, su_CStringArray, suObList, moLogs_c, moStamp_c …), so reading it would give the
number directly; that is still to do. SW2011 streams end right after the last slot, with no trailing
u16.

The SW2011 class layouts are handled under `r.legacy`. The full SW2011 / SW2022 table is in EXP-080
§3.2, which compares a 2011 cube, its 2022 re-save and a native 2022 cube field by field. In short:
the node has no comment string and no u32 c, and its tail is 54 bytes, u16 2, u32 state, where 2022
inserts four u16 before the u32. The component is 43 bytes instead of 79, and sketch handles have
no trailing u32. The document object is pre-loaded from Config-0, the face name tail is 6 bytes, and
the display dimension blocks are shorter.

Status (2026-10-05): all 25 SW2011 models read to the end, as do all 24 SW2022 ones.
