# EXP-108: display edge-type numbers (300x / 480xx) and the record after the edge table

The type number is the native edge's curve class, with no exceptions in 34,850 edges. The 300x
and 480xx forms are two dialects of one field, chosen per file by the DisplayLists version (300x up
to 15000, 480xx from 16000). In 480xx the last digit adds an edge-sharing code: tangent, boundary,
or neither. It does not encode convexity. The bytes after the edge table start with a
persistent-id string for the face, and I could decode only that part.

Answers NQ-032 in part. Not proved by blind prove and disprove agents: I had no way to spawn
them here. The controls below are my own, so treat this as one author's result.

Scripts and outputs: `scripts/EXP108/` (`rows.js`, `edges.js`, `analyze.js`, `variant.js`,
`smooth.js`, `family.js`, `dialect.js`, `control.js`, `tailsurvey.js`, `krefs.js`, `tail2.js`;
outputs in `out/`). Converter `dev` 9cf5003, read only. Reference: the native B-rep joined with
`src/brep/display-join.js` (EXP-104/107), edges matched by the section id the edge table stores.

## Setup (measured)

- 115 modern parts with an id block. 34,850 native edges carry a display type number on at least one face; 68,504 face sides (each edge is listed once per face using it).
- A side is used only when the join to the native face is by id, type or geometry, and the face has one record for the edge. Unmatched records: 145 of 68,616 name an edge id the joined native face lacks (the EXP-107 parts with stale ids).
- Convexity reference: outward normals from the native surface and face sense, at the edge midpoint (chord start point for intersection curves). Control: the cube `C00_cube_10mm` gives all 12 edges convex (s = -1, angle 90 degrees).

## Results (measured)

1. **Which family a file uses.** 83 parts use only 300x, 29 use only 480xx, 0 mix. By DisplayLists version: 11000 (6 parts), 12000 (12), 13000 (8), 14000 (5), 15000 (52) are 300x; 16000 (14), 17000 (14), 18000 (1) are 480xx (`out/family.txt`). The split is exact on this corpus. SolidWorks release years fit too (online 2023 and later are 480xx, 2022 and earlier 300x, apart from one 2024 part at 15000), but the version number is the cleaner key.

2. **300x is the curve class.** 3001 line, 3002 circle, 3003 ellipse, 3004 intersection, 3005 B-spline, 3006 spcurve. A trimmed curve counts as its basis curve. Over 34,850 edges the class matched with 0 exceptions, and the two faces sharing an edge always carry the same number (19,942 of 19,942 two-sided 300x edges, 13,712 of 13,712 for 480xx). Counts: 3001 22,590 sides, 3002 14,336, 3003 164, 3004 699, 3005 2,158, 3006 166 (`out/analyze.txt`).

3. **480xx is 48000 + 16 x class + j.** Same classes (line 1 ... spcurve 6), again 0 exceptions. j is -1, 0, 1 or 2 (480xx edges: j=0 8,795; j=1 2,377; j=2 966; j=-1 2,541).
   - **j=2 is a boundary edge** (used by one face only). 966 of 966 edges with one face use have j=2, and all j=2 edges have one use. No exceptions either way (`out/smooth.txt`).
   - **j=1 is mostly a tangent edge.** Of the two-face edges with j=0 or 1 and a measured angle: j=1 has 2,114 at angle below 1e-6 rad, 26 between 1e-6 and 1e-3, 29 between 1e-3 and 1e-2, 14 between 0.01 and 0.05, and 1 above 0.5. j=0 has 17 at angle below 1e-6, 38 between 0.01 and 0.05, 175 between 0.05 and 0.5, 8,552 above 0.5. So the angle at the sample point separates them in 96.8% of j=1 edges and 99.8% of j=0 edges. The misfits are not explained. The 17 j=0 edges at zero angle are all cylinder/torus intersection curves in 2 parts (angle was measured at one point only; I did not sample along the edge). The 70 j=1 edges at a measurable angle may be near-tangent within some tolerance, or edges whose angle varies along the curve; not checked.
   - **j=0 does not separate convex from concave.** 48016 (line, j=0) holds 7,376 convex and 3,852 concave edges. Convexity is not in either family. 3001 holds 12,414 convex, 4,588 concave and 5,588 tangent by the same measure.
   - **j=-1 is a file-level dialect, not an edge property.** All 2,541 such edges are in two parts (`a4ecc6f5_PP-2074-08`, `PTC GE8080-8`; both 17000, but the other 12 17000 parts use j=0/1/2). In those parts every edge has j=-1, tangent or not (of 2,539 measured: 834 below 1e-6 rad, 281 between 1e-6 and 1 rad, 1,424 above 1 rad). Neither part has a boundary edge (0 of 2,541), so I cannot say whether j=2 would appear there. Reading the digit as `-1 + code` with code 0 = "not classified" fits, but that is a guess.
4. **Control.** Pairing each edge's number with the curve class of another edge of the same part (shift of 7) matches 60.0% of 34,850 (46.3% of the 14,639 non-line edges). The chance level is high because lines and circles dominate, so the 100% match is the evidence and the control only shows the test can fail.
5. **Face-type pairs add nothing.** Within a curve class and j, the pair of face surface types varies freely (class 1, j=0: plane/plane 5,125, cylinder/plane 325, cylinder/cylinder 63, ...). No number depends on the pair beyond what the curve class and tangency imply.

## The record after the edge table (partly measured)

Tail = bytes from the end of a face's edge table to the next face record. 13,533 faces, all non-empty.

- It starts `0, 0, 1, K` (or `0, 0, 0, K`) in 13,293 of 13,533 faces (98.2%); the rest start with a double instead of the first two zeros. K runs from 101 up past 600. It is not an id of the string that follows: 286 of 291 distinct K values in a part cover several different strings, and 6 strings take several K values (`out/krefs.txt`). What K counts is not found.
- A UTF-16 string follows in 10,446 faces, after an `ff fe ff 1f` marker (seen in the cube; the marker was not counted across the corpus). It is a persistent-id text for how the face was made, for example `moSimpleSurfIdRep_c,N,N,` (4,765), `moFromSktEntNIntSurfIdRep_c,N,N,-N,N,` (2,150), `moFilletSurfIdRep_c,N,N,` (969), `moFromSktEntSurfIdRep_c,N,N,` (580), `moEndFaceNIntSurfIdRep_c,...` (480), mirror and pattern forms nest others in angle brackets (`out/tailsurvey.txt`). 3,087 faces have no such string; their tails are exactly 52 bytes (846 faces) or 60 bytes (2,241). Some of the 10,446 strings are not id text (`defaultplastic` 165, a part name 108).
- In the cube's first face the string is followed by `10`, a count equal to the edge count (4), then 28-byte entries `id, u32, u32, double, double` whose ids are the face's edge ids in edge-table order (62, 82, 5, 79) and whose doubles are 0 or 0.01 (the cube edge length in metres, or something equal to it there). That layout does not hold in general: other cube faces (face 4) carry a different layout, and across the corpus the table's edge ids appear in the tail in table order for only 6,771 of 13,525 faces, with 33,268 ids found and 36,113 not found. The doubles' meaning is not tested.
- So the tail is a sequence of objects whose layout depends on the id-rep class. I decoded the head and the string, not the objects.

## Ruled out

- The type number as a convexity (concave/convex) code: 48016 and 3001 each hold both in the thousands.
- 300x and 480xx as different edge categories inside one file: no file mixes them.
- Face-type pairs as a factor in the number.
- K as an id of the persistent-id string.
