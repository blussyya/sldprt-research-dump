# EXP-091: surface parameters, LocalBodies framing, and configuration bounds

EXP-090 left three small format questions that the expanded corpus could answer without another
SolidWorks save. This experiment checks them over all 222 part paths under `test files original`,
`test files new`, and `test files online`.

Scripts and generated JSON are under `scripts/EXP091/`.

## The optional scalar arrays are surface parameters

The two optional float arrays occur on 1,545 faces and 205,327 vertices in 37 files. They have one
value per display vertex. Their stored order was evaluated against the exact native surface in the
controlled cone, sphere and loft files:

| surface | faces | vertices | largest stored-order point error | smallest swapped-array maximum |
|---|---:|---:|---:|---:|
| cone | 1 | 144 | 1.09e-9 m | 6.88 m |
| sphere | 1 | 5,004 | 1.24e-9 m | 0.0100 m |
| B-surface | 4 | 1,776 | 2.29e-6 m | 0.0129 m |

The cone's second parameter is axial distance, matching the file's cone convention established in
EXP-085. The B-surface gap is between the saved display point and the exact surface point at its
stored parameters; those mesh vertices are approximate. A blind check projected independent native
surface feet and reproduced the parameter correspondence.

This identifies the arrays as per-vertex surface parameters, conventionally `(u,v)`. The direct
geometric check covers tags 4003, 4004 and 4006. The same pair occurs on tags 4007–4010 and four
records with an undecoded tag, but those surface families were counted rather than evaluated here.

## LocalBodies is a named entry table

The corpus contains 41 `LocalBodies` streams. Every stream begins with an entry count. Each entry
starts with an MFC UTF-16 CString name, a 10- or 18-byte header, and one or more bounded Parasolid
section frames.

| item | result |
|---|---:|
| named entries | 281 |
| section frames | 289 |
| streams ending exactly after their last entry | 41/41 |
| entries with more than one section | 2 |
| zero eight-byte section tails | 289/289 |
| single-chunk zlib sections | 287 |
| multi-chunk zlib sections | 2 |

The two multi-section entries are the motherboard import in `34fe5ff1` with two sections and
`ST3215_C018_04.step<1>` in `2e6e140a` with eight. A ten-byte continuation header separates their
sections: five zero bytes, `u32le(next section size + 5)`, then one zero byte.

Two large sections use repeated `u32le inflated | u32le compressed | zlib` chunks inside one outer
frame. `60f84235` has 48 chunks and `a4ecc6f5` has 205. All 253 chunks inflate to their declared
length and meet the eight-byte tail exactly. Together with the 287 ordinary sections, the survey
validates 540 chunks.

The entry header's 10- and 18-byte field meanings remain unnamed. All 289 tails are zero, so their
value is established for this corpus but their intended role is still unknown.

## The configuration record is an overall saved-display envelope

The configuration-level bounds are recognizable without choosing candidates by their numeric box:
an MFC UTF-16 configuration name ends eight bytes after the 132-byte bounds record begins. This
finds 113 records in 113 of 166 readable modern files. The names are ordinary configuration names,
including `Default` and translated equivalents.

Of the 113 records, 112 equal the union of all saved display-face bounds. The exception is
`ac760485_存矿小端.SLDPRT`: its configuration record extends 4.412 mm below the display in x and
12.684 mm above it in z. The active native body has the same box as the display, so that one record
is an older, padded, or broader envelope; this experiment cannot choose among those causes.

No record with this name-and-layout signature occurs in 36 readable legacy files. Twenty files are
outside this comparison because their display stream is absent or not readable by this extraction
path. The record is therefore common in modern saves, especially the controlled and recent files,
but is not a universal DisplayLists feature.

This corrects EXP-064's count of 47 configuration records in 45 files. `Dekor` and
`Helical Bevel Gear` each have one real named configuration record plus a later arithmetic match
whose bytes do not carry the MFC name relationship. EXP-064 counted both later matches as second
configurations. The bounded name signature gives one configuration record in every file from that
older 45-file set.

## Reproduction and limits

From the repository root:

```text
node knowledge/evidence/scripts/EXP091/scalar-parameters.js
node knowledge/evidence/scripts/EXP091/localbodies.js
node knowledge/evidence/scripts/EXP091/configuration-bounds.js
```

The scripts retain raw entry headers, names, offsets, boxes, chunk lengths, and per-control errors
in their JSON outputs. A fresh blind validation checked the three conclusions without changing the
scripts. It caught the first LocalBodies pass treating the two large frames only as bounded blobs;
the final script now inflates and checks every chunk.
