# EXP-111: the modern per-feature Created and Modified records

NQ-060 is answered in part. Modern files keep two per-feature time records, and neither is in
Biography. Modified is a sub-second FILETIME at the end of every feature node. Created is a
unix-second stamp in each History-folder item. Created is proven for non-sketch features and
inferred for sketches, and no blind agent has checked either yet.

Scripts and outputs are in `scripts/EXP111/` (`out/*.log` next to each script). Nothing was moved
into the converter or the format write-up.

## What was found

| | Modified | Created |
|---|---|---|
| Where | last 8 bytes of the 54-byte node tail (tail offsets 46..53) of every feature | `moCompFeature_c` inside each `moHistoryFeatItemData_c` in the History folder: u32 feature id, then u32 unix time |
| Encoding | FILETIME, high u32 first, then low u32 (Win32 struct order gives dates 50,000 years out) | unix seconds |
| Resolution | 100 ns (readings look like 0.3 s steps) | 1 s |
| Present in | SW2011 and SW2022 files | native SW2022 files only |

Same Created value also sits in the `moFR_c` face-name references (the u32 after the feature id).
EXP-079 already read both fields and left them unnamed.

## Modified: the node-tail FILETIME

Reading 2,504 feature nodes in 205 parts gives 2,456 plausible times. The rest are zero (for
example Sensors in SW2011).

**Control with known answers (measured).** The 25 SW2011 controlled files keep an old-style log
of Created/Modified unix times per feature in Config-0 (EXP-081). For the 74 modelled features
there (`out/cmp2011b.log`):

- 39 non-sketch features (extrude, cut, fillet, chamfer, shell): floor(FT) equals the log's
  Created time in 39 of 39. These features have no Modified record.
- 35 sketches: floor(FT) equals the log's Modified time in 26 and is 1 s later in 9. Never earlier.
  The log's Created time for a sketch is 1 to 2 s before that.

So the FILETIME is the Modified time: the last time the feature was changed, with sub-second
precision the old log didn't have. C22/C23 show it directly: Sketch1 Created 09:41:35, Modified
09:41:36, FT 09:41:36.797; Boss-Extrude1 Created 09:41:37, FT 09:41:37.392. The SW2011-to-2022
upgrade (C23) copies the field byte for byte.

**Offset control.** Sliding an 8-byte FILETIME window over every offset of the tail, both word
orders, for 212 modelled features: only offset 46, high word first, lands between the file's
ModelStamps time and its last Biography snapshot, 212 of 212. The one other hit (offset 42, low
first, 21 of 212) reuses the same high word with garbage as the low word, so it only lands by
chance inside the 7-minute span one high word covers (`offset_control.js`).

**Bounds from the file's own save times (measured, 71 parts with at least two modelled features).**

| bound | result |
|---|---|
| first feature FT minus ModelStamps time | min +1.83 s, median 4.31 s, 0 below zero |
| last Biography snapshot minus last feature FT | min +0.10 s, 71 of 71 at or above zero |
| `core.xml` modified minus last feature FT (45 parts with the tag) | min -0.67 s, none below -1 s (core.xml has whole seconds) |

Default folders and planes carry the document-creation time: in 70 of 95 parts their FT floor
equals ModelStamps exactly. In the other 25 it doesn't, so ModelStamps is not always the creation
time. (Seven online parts have upgrade-added folders stamped years after ModelStamps; those are not
modelled features and are not counted above.)

**Order counter (measured).** Each node already had a u32 the reader called `order` (101 for
default items, then 103, 105 ...). It tracks last modification, not creation:

- FT against `order`: 353 pairs in 71 parts, 0 inversions.
- `DLUpdateStamp` equals the Features XML `swLastModifiedStamp` and equals max(`order`) + 1 in 39 of
  39 fully read parts (C07: 112 = 111 + 1). So DLUpdateStamp is a document change counter, not a
  time, and `order` is each feature's value of that counter at its last change.
- Helical Bevel Gear: Sketch4 (id 82) has order 169 and FT 08:31:42, Sketch7 (id 90) has order 162
  and FT 08:28:21. Order and FT agree with each other against id order. FT breaks id order in 5 of
  353 pairs, all in this one file.

## Created: the History item stamp

For 133 History items in 87 parts, joined to feature nodes by id (`out/created_checks.log`):

- stamp never exceeds floor(FT): 0 of 133 violations.
- Equal to floor(FT): 81. Non-sketch features: 68 of 72 equal, 4 earlier by more than 10 s.
  Sketches: 13 equal, 39 earlier by 1 to 10 s, 9 earlier by more than 10 s.
- Equal to the `moFR_c` stamp where both exist: 70 of 70. In the SW2011 control the `moFR_c` stamp
  equals the log's Created time in 37 of 37.
- Ids are handed out at creation. Stamp order against id order: 0 inversions in 197 pairs
  (40 parts). Stamp order against the `order` counter: 1 inversion in 197, the gear's Sketch4/Sketch7.
- Control: pairing each stamp with the next feature's FT in the same file gives equality in 15 of
  132 pairs, against 81 of 133 for the true pairing. "stamp not after FT" alone is weak (97 of 132
  shifted pairs pass it), so equality and the FR link carry the claim.

Where Created and Modified part ways (measured, production files):

- Helical Bevel Gear: Revolve1 created 06:21:10, FT 08:26:11. Sketch9 created 08:35:56, FT
  08:54:09.974, and Loft2 (created 08:32:42) has FT 08:54:09.968. Sketch10 created 08:55:58, FT
  08:56:55.235; Cut-Extrude1 FT 08:56:55.245.
- `cube.SLDPRT` Sketch2: created 01:09:25, FT 01:10:20.725; Boss-Extrude1 FT 01:10:20.739.
- Seven `moFR_c` stamps sit before their FT by 19 s to 2 days (`out/frall.log`).

Pairs like Sketch10 and its cut share FT to about 10 ms. A sketch's Modified time moves when the
feature that consumes it is built.

**Coverage.** Of 138 modelled features in parts with a History folder, 132 have an item. The six
without: C23's two (upgraded from SW2011; the upgrade adds the folder but no items), and Helical
Bevel Gear's Sketch1, Revolve1 and Sketch2, and ReducerBox's Sketch1. The gear's three are the
oldest features in the file, so features made before the folder existed probably get no item (guess).

## Independent raw check

`independent/raw_check.js` doesn't use the object reader. Feature ids come from the KeyWords XML,
history records from a byte scan for (id, time) pairs, FILETIMEs from a byte scan, paired by stream
order. On the 24 SW2022 controlled files: 59 of 60 expected ids found (the missing one is C23's
upgraded Sketch1; its one hit in C23 is a face-name reference, which has the same layout), 59 of 59
paired FT at or above the stamp, 28 equal, 0 below. FILETIMEs ran in stream order in 23 of 24 files;
C23 doesn't, because the upgrade appends fresh folders after carried-over features.
An earlier version of this script found one "FT below stamp" in C16. Cause: it skipped the user
plane Plane1, which shifted the pairing. The reader-based check had no violation. Fixed by adding
user planes, not by relaxing the comparison.

## Ruled out

- **Biography** (already ruled out by EXP-088). No per-feature field; its snapshots only bound the
  last save (FT never later than the last snapshot, 71 of 71).
- **`DLUpdateStamp`** is a counter (112 in C07, equal to `swLastModifiedStamp`), not a time.
- **`created`/`modified` version pairs** in the node (15000 / 2022009, 4700 ...) are release and build
  codes, constant per file generation.
- **Other tail bytes.** Over 212 modelled features only bytes 5 and 32 (flags) and 46..53 (the FT)
  vary; `e`, `g`, `h` and the second string are constant.
- **Whole-stream scan of C07** for unix-time u32s or FILETIME pairs in the save window finds only
  these two records plus `moFR_c` copies and the document-creation folders (`out/scan_time_like_C07.log`).
  Not repeated on other files.

## Not checked yet

- **No blind prove/disprove agents ran.** This session has no way to spawn them. The method calls
  for both before this goes into the docs. The raw check above is separate from the reader code but
  uses the same offsets and my reading of the field, so it does not replace them.
- **Sketch Created times.** Proven only by analogy: the stamp precedes FT by 1 to 10 s as the SW2011
  log's Created precedes Modified, and it equals the `moFR_c` stamp, which is Created for the 37
  non-sketch features of the control. No modern file has a log for sketches to confirm it directly.
- **Modified means edit, regenerate, or both.** A feature rebuilt without being edited might not
  touch the FT. The gear's pairs sharing an FT to 10 ms look like single edits, but no file here
  edits one feature and keeps the dependants' FT unchanged.
- **`modified.x`**, the f64 beside the version stamps. It holds small values (0, 0.015, 0.016, 0.031,
  0.046). Possibly a rebuild duration; not tested.
- **Reader coverage.** 141 of 205 feature trees stop early on unsupported layouts, so only 71 parts
  gave two or more modelled features; features after the stopping point were not read.
- **Multi-configuration parts, configuration-specific features and suppressed or deleted features**
  were not examined. The `order` gaps (C07: 109 missing) suggest deleted features but that is not
  checked.
- Meaning of the other 22 bytes in `moHistoryFeatItemData_c`.

> **Checked 2026-11-09 (blind prove and disprove, own scripts, EXP-111 scripts not read):**
> - The converter has no feature-node reader. The disprove check used the EXP-079 research reader, and the prove check read bytes by hand, so neither is fully independent of earlier research code. Coverage is small: 42 readable modern files with a time window (143 user features, 135 History items).
> - Modified time: the FILETIME at tail offset 46, high word first, falls inside the file window for 142 of 143 user features. No other offset, word order or epoch comes close (0 to 2 of 143). The window's upper bound has to be max(core.xml, last Biography time). core.xml alone is up to about 5 minutes early, and features sit up to 0.7 s past its whole second.
> - Exceptions the window does not cover:
>   - Template-default nodes in native SW2022 files (planes, origin, folders) all carry 2026-08-12T23:11:14Z, which is before the file's ModelStamps. That is the template's time, not the file's. In the upgraded C23 the same nodes carry session time.
>   - The material node "Brass" in Helical Bevel Gear is 12 days before ModelStamps.
>   - Some German "Kommentare" folders have an all-zero tail.
> - The SW2011 log comparison is unresolved for sketches. The prove check matched 36 of 45 sketches to the log's Created time exactly and none to Modified, but only 3 of the 45 have a Modified entry. EXP-111's "sketches match Modified or 1 s later" needs to be rechecked against that. For non-sketch features, 153 of 690 log Created times match a decoded time in the same file, and a +1 day control matches 0. The 442 template defaults match none, which agrees with the exception above.
> - History items: all 135 link to a `moCompFeature_c` with a feature id. 0 of 135 stamps are later than Modified, and 85 equal floor(Modified). They are non-decreasing with feature id, not strictly increasing: 11 adjacent pairs share a second. Whether the stamp is Created or a first-touch time can't be separated from these data.
> - DLUpdateStamp is not a time: 216 files, values 101 to 14,536. It equals the ModelStamps counter in 190 of 216 files and differs by -191 to +152 in the rest. In the SW2011 cube series it steps by 2 per feature. C04 reads 113 and C05 reads 112 with the same feature count, so it is not a count of operations. "max(order)+1" was not reproduced: the prove check compared it to the Config-0 log ordinals, which is a different counter, and the disprove check did not extract `order`.
