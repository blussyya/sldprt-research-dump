# EXP-088: Block3, ghost bodies, and the two histories

This experiment picked up four things that had been grouped together as "the history": Block3 in
the display mesh, bodies in `GhostPartition`, the feature archive in `ResolvedFeatures`, and the
`Biography` stream. They are separate records and answer different questions.

Scripts and full outputs are under `scripts/EXP088/`. This is a draft for review. Nothing from it
has been moved into the converter or the public format write-up yet.

## Block3 is structured data

The old corpus had only zero Block3 bytes. The expanded online sample does not.

Two independent probes recovered Block3 from the raw display stream and checked it against the
current parser. The blind probe read 124 of 142 online paths: 19,280 accepted faces and 1,903,076
Block3 bytes. It found 30,713 nonzero bytes in 27 files, with no raw/parser disagreement. The only
values were 0, 1, 2 and 4.

Block3 has one byte for each Block1 word. The byte's position matters:

| Block1 position | byte 1 | byte 2 | byte 4 |
|---|---:|---:|---:|
| strip control | 2,690 | 0 | 16,455 |
| nonzero edge label | 11,322 | 246 | 0 |
| zero edge label | 0 | 0 | 0 |

Byte 4 only occurs at later strip controls. Byte 1 occurs at the first strip control and at edge
labels. Every interior position, where Block1's edge label is zero, also has a zero Block3 byte.
That is enough to reject the description of Block3 as unused padding. The meanings of the strip
control bytes are still unknown.

### Edge bytes

A fresh check joined display faces to the selected native body by face ID, then accepted an edge
only when it occurred in that native face's loops. For two-sided edges it compared the stored
normals on the two face uses at shared display vertices.

| Block3 bytes on the two uses | edges | under 0.001 rad | over 0.05 rad |
|---|---:|---:|---:|
| 0 / 0 | 1,974 | 10 | 1,961 |
| 1 / 1 | 371 | 363 | 0 |
| 0 / 1 | 102 | 102 | 0 |

Every edge with byte 1 on either use was smooth or nearly smooth in this check. All 102 mixed
uses joined a plane to a cylinder or cone, with byte 1 on the curved face. This makes byte 1 a
per-face edge-use marker, not a property stored once on the topological edge.

Byte 1 is not required on every tangent edge. Ten 0/0 edges were tangent within 0.001 rad, all in
`3c4752f1`; most are analytic-to-B-spline joins. The result supports "smooth/tangent edge use" but
does not yet distinguish geometric classification from a display treatment for tangent edges.

Six native edges in the joined subset had only one owning face. They covered 66 annotated mesh
segments, all with byte 2. No joined two-owner edge had byte 2. This supports "open boundary" for
byte 2, but the other byte-2 labels belong to faces or bodies this check could not join.

The checks also rejected three simpler readings. Byte 4 does not reverse triangle winding, byte 1
is not determined only by edge ID, and byte 2 does not mean a same-face seam.

Evidence:

- `scripts/EXP088/block3/`: raw survey and topology probes.
- `scripts/EXP088/block3-independent/`: blind raw recovery and counterexamples.
- `scripts/EXP088/block3-tangent/`: blind native-face join and continuity check.

## Ghost bodies link to feature references

`GHOST_REF_BODY_ID_2001` is a document-local join key. Its integer value equals the first
little-endian u32 in the feature archive component block currently called `@comp.x0`, at component
object offset +17.

The main and blind probes both checked all 49 controlled files. Their 54 ghost bodies joined 54
component references, with no unmatched IDs or duplicates. The blind probe compared the 28-byte
component block to the raw feature stream and used two negative controls: adding one million to
the ID, and reading the next u32 instead. Neither control produced a match.

Fifty bodies have no edge, one vertex, and one point at (0,0,0). Every reference is a
`moCompSketchEntHandle_c` naming feature 5, `Origin`. The repeated point is therefore an Origin
reference used by a sketch, not an unexplained copy of the finished solid.

The other four bodies are in the two C16 loft files. Their `moCompProfile_c` objects name Sketch1
and Sketch2. The lines and circle counted in EXP-078 belong to the boundaries of the two sheet
bodies; the two point-only bodies do not contain profile wires.

An independent production check found no ghost partition or component IDs in `cube.SLDPRT`. In
the helical gear, all seven ghost bodies joined uniquely: three profile sheets used by Loft2 name
Sketch2, Sketch4 and Sketch7, and four edge-free bodies used by Sketch1, Sketch2, Sketch9 and
Sketch10 name Origin. Raw component blocks again matched at object offset +17, with no unmatched
or duplicate IDs. This is one production part with ghost geometry, not production-wide coverage.

This proves a reference, not creation ownership. The IDs repeat between documents, and the other
24 bytes of the component block remain unnamed.

Evidence:

- `scripts/EXP088/ghost/`: the first join and all controlled rows.
- `scripts/EXP088/ghost-independent/`: blind raw-offset check and negative controls.
- `scripts/EXP088/ghost-production-independent/`: blind cube and helical-gear check.

## The binary feature tree is useful before every field is decoded

`scripts/EXP088/features/export.js` turns the existing research reader's objects into an
inspectable tree without flattening every object reference into a dependency. It exports feature
names and IDs, archive indices and byte ranges, recorded child links, contextual feature
references, and the items in the History folder.

For example, C07 records Boss-Extrude1 (32) with Sketch1 (26) as its child, and Cut-Extrude2 (46)
with Sketch2 (33). Its History folder records Sketch1, Boss-Extrude1, Sketch2 and Cut-Extrude2 in
that order. Plane references, body naming references and self references keep their source class
and field path instead of being called rebuild dependencies.

The strict survey covers the 49 controlled files and nine top-level original parts:

- 50 of 58 consume their advertised top-level slots and end at the stream boundary.
- C23 advertises 19 slots but reaches exact EOF after 18. The old EOF-only check hid this mismatch.
- Seven other files stop on an unsupported layout or have no `ResolvedFeatures` stream.
- The 50 strict reads contain 124 resolved child links and 81 History items that resolve to a
  single feature ID.
- The reader still scans over 99 dimension-placement stretches totalling 51,151 bytes. Those
  bytes are retained as undecoded ranges. Reaching EOF is not being used as a claim that they are
  understood.

As a separate check, the `KeyWords` XML agrees with the binary feature ID and name for every
controlled feature it lists: 503 comparisons, zero mismatches. The XML also agrees with the nine
`DissectableChildren` links present in that sample. It does not validate the opaque fields or give
a complete rebuild dependency graph.

A fresh focused probe independently recovered C07's Boss32→Sketch26 and Cut46→Sketch33 child
links, and its History order 26, 32, 33, 46. Across C00, C04, C07, C16, C23 and C24, 126 binary
ID/name pairs matched `KeyWords` with no mismatch. It also read C23's raw count of 19, consumed 18
top-level objects and landed at exact byte 11,481 with no null slot or padding. Its opaque
dimension-placement scan lies inside C23's last object, so the count/EOF fact holds while the last
object is still not byte-for-byte decoded.

Three gear references use the sentinel feature ID `0xffffffff`, while three inline hidden
features share that ID. The exporter reports all candidates instead of choosing one without
context.

Evidence: `scripts/EXP088/features/`, `scripts/EXP088/features-independent/`, and the blind check
in `scripts/EXP088/features-blind/`.

## Biography is save-environment history, not feature history

`Biography` now has a sequential reader. It consumes all 216 Biography streams in the 222 local
part paths: 3,519 records, each ending exactly at the stream boundary. Six paths have no Biography
stream. The reader does not scan forward.

The stream is an MFC `moBiography_c` object followed by a u32 record count. Each record has nine
u32 words, a CString and a u16, then exactly two snapshots. Each snapshot has three u32 words and
six slots of CString plus three u32 words.

The first two record words match release and build-date codes from the independent `History`
stream in C22, C23, C24, head_back and the helical gear. C23 preserves C22's first two Biography
records byte for byte and appends one record.

The first two snapshot words form a plausible Windows FILETIME. In all five checked files, one
snapshot's whole-second value equals the first `ModelStamps` word. The remaining words look like
Windows environment and path metadata, but most do not have verified names yet.

A second reader, written without the first parser, reproduced the byte boundaries on C22, C23,
C24, the original and re-saved head_back, and the gear. It rejected truncations, bad class and
count fields, and bad string lengths. The main parser rejected all 1,771 proper truncations of
C22 plus three framing mutations.

Biography does not contain the decoded feature operation history. The earlier suggestion that the
SW2011 feature log moved there in modern files is unsupported. Nothing decoded in Biography says
whether head_back was saved by an API, batch job or interactive session, or whether graphics were
redrawn.

Evidence: `scripts/EXP088/history/` and `scripts/EXP088/history-independent/`.

## What is left

- Change one SolidWorks tangent-edge display setting at a time and compare the files. That would
  separate Block3's geometric classification from rendering treatment and explain the tangent
  0/0 exceptions.
- Name the strip-control bytes in Block3.
- Extend the ghost join across production parts and configurations, then decode the remaining 24
  component bytes.
- Replace the feature reader's dimension-placement scans with bounded field layouts and resolve
  inline features that share `0xffffffff`.
- Find the modern equivalent of SW2011's per-feature Created/Modified log. Biography is not it.
