# EXP-063 — Independent STEP comparison exposes non-tight spline bounds

Date: 2026-09-21. Base: staging `32cc4410b0b130242791ba2984640bc268b65a4d`.

## Result

The union of decoded DisplayLists face boxes agrees with independent STEP geometry bounds within 1e-9 m on **23/24** SW2022 models (19/24 within 1e-12 m). The exception is **C16_loft_spline**: its stored box extends approximately **10.365153286 micrometres on all six sides** of the STEP geometry box. The tessellation bounds instead agree with STEP within 2.236e-10 m.

This is an empirical counterexample to treating every stored box as a tight bound on the corresponding STEP geometry. It supports a conservative/padded bound interpretation for this model. It does not identify the padding algorithm or prove whether the native kernel's own representation has exactly the same extrema as STEP.

## Method and reproducibility

Run from the repository root:

```sh
python3 v0.4.9/exp063_step_bounds.py
```

Dependency used: `cadquery-ocp` version **7.8.1.1.post1**. Results: `v0.4.9/EXP063_RESULTS.json`, including script/input SHA-256 hashes, all 24 native/STEP pairs and numeric boxes. It reads the committed EXP-062 gzip evidence, verifies each native file hash, and unions its independently decoded face boxes. STEP geometry is loaded separately by OpenCascade. `BRepBndLib.AddOptimal` runs with **useTriangulation=False**, first with **useShapeTolerance=False**, then with it enabled as a sensitivity control. This uses numerical geometry bounds; it is not a formal exact-arithmetic proof.

The STEP exports' millimetre unit declarations are checked. OpenCascade's default millimetre target is converted to metres. C00's independently read box is asserted against `[0,0,0,0.01,0.01,0.01]` as a unit/orientation control. No alignment fit or scale fit is performed. Comparing whole-model unions avoids assuming native faces correspond one-to-one to STEP faces, since periodic faces can split on export. Consequently this experiment does **not** establish every individual face box's tightness, particularly for internal holes.

## C16: quantitative counterexample

All values below are metres, ordered x/y/z:

| Source | Minimum | Maximum |
|---|---|---|
| STEP geometry, no shape-tolerance enlargement | -0.005, 0, -0.005 | 0.005, 0.01, 0.005 |
| Stored DisplayLists box union | -0.005010365153286359, -0.000010365153286359439, -0.005010365153286359 | 0.005010365153286359, 0.01001036515328636, 0.005010365153286359 |
| Mesh bounds | -0.004999999888241291, 0, -0.004999999888241291 | 0.004999999888241291, 0.009999999776482582, 0.004999999888241291 |

Enabling OpenCascade shape-tolerance enlargement adds approximately **0.82944 micrometres** on each side, substantially less than the stored **10.36515 micrometres**. Thus this alternate reference calculation does not erase the discrepancy. Do not equate this numerical enlargement with a decoded native padding field.

## Positive evidence beyond float32 mesh bounds

For the full torus C15, the stored box agrees with STEP within about **1e-10 m**, while the mesh box differs by **6.307266e-6 m**. For the torus quarter C17, the corresponding differences are about **1e-10 m** and **8.156108e-7 m**. These cases independently support the stored bounds as useful geometry bounds that can be more accurate than bounds computed from displayed vertices. The spline exception shows why that observation must not be promoted into universal exact tightness.
