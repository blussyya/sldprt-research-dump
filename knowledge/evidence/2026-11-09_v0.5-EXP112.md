# EXP-112: the modern container is a ZIP archive in disguise, and it has a directory

2026-11-09. A modern SLDPRT is a ZIP archive from byte 8 on, with three changes: per-file
signatures, offsets counted from byte 8, and filler that imitates headers. Its central directory
lists every stream: 7,895 entries in 178 distinct files, all of which inflate and pass their
CRC-32, and the signature scan finds no stream outside it. A reader no longer has to scan.

A blind prove agent confirmed the directory on all 181 modern files and corrected one number
(below). The blind disprove agent ran out of usage before it gave a verdict.

Prior art: PRIOR_ART.md already notes that cadmpeg documents a "tail directory". This work didn't
read it. Everything here comes from the corpus.

Scripts and outputs: `scripts/EXP112/` (`*.out` beside each script, `table.json` has one row per
file).

## Layout

```
0      4 bytes   key: four successive rand() & 0xff of the Microsoft C runtime generator
4      00 00 00 04
8      filler
       local header, name, raw DEFLATE data     <- repeated per stream,
       (sometimes one filler block)                in increasing offset order
       central directory: one 46-byte record + name per stream, back to back
       filler shaped like central records
       filler shaped like end records, with the one real end record among them
```

Local header, central record and end record have their fields at the ZIP positions.

| record | field | value |
|---|---|---|
| local, +0 | signature | per file |
| local, +4 | version, flags, method | 20, 6, 8 in 7,895 of 7,895 |
| local, +10 | 4 bytes at the time/date position | not decoded, see below |
| local, +14 | CRC-32, compressed size, size, name length, extra length (0) | as already documented |
| central, +0 | signature | per file, not the local one |
| central, +4 | version made by 0, version needed 20, flags 6, method 8 | 7,895 of 7,895 |
| central, +12 | the same 4 bytes as local +10, then CRC-32, sizes, name length | equal to the local header in 7,895 of 7,895 |
| central, +30 | extra length 0, comment length 0, disk 0 | |
| central, +36 | internal attributes | 1 on 2,148 entries (the XML streams), 0 on 5,747 |
| central, +42 | local header offset, **counted from byte 8** | |
| end, +0 | signature | per file, a third value, occurs once in the file |
| end, +4 | 4 zero bytes | |
| end, +8 | entry count, twice | |
| end, +12 | directory size, up to the end record, filler included | |
| end, +16 | directory offset, **counted from byte 8** | |
| end, +20 | 0 | |

Names are rotated in both places, as in the local header.

## Finding the real end record

A file holds 10 to 17 end-record shapes (4 bytes, 4 zeros, a count twice, two u32s, a zero u16).
Exactly one satisfies `position == 8 + offset + size`. That one also walks: `count` central
records from `8 + offset` share one signature, and the local headers they point to share another
and repeat the record's CRC, sizes and name.

| check | result |
|---|---|
| modern files with exactly one end record that passes | 181 of 181 (`table.out`) |
| directory entries (178 distinct files) | 7,895 = the 7,374 nonempty + 521 empty streams EXP-097 counted |
| entries that inflate to the declared size | 7,895 |
| entries whose CRC-32 matches | 7,895 |
| name sets equal to the converter's scan, bytes equal | 178 of 178 files |
| duplicate names | 0 |
| entries in increasing offset order | 178 of 178 files |

Control: flipping one bit of a central record's CRC makes the walk reject the file, and a file
cut in half has no directory (`converter-check.out`, converter test `container.test.js`).

## Filler

Measured as next header minus end of previous data (`filler.out`).

- Between streams: nothing in 5,983 places, one block in 1,734. A block is 85 to 100 bytes and
  each file uses one size.
- Before the first header: 255 to 900 bytes, a whole multiple of the file's block size in 178 of
  178 files.
- Between the last stream and the directory: nothing, 178 of 178.
- After the last real central record, filler central records with random signatures. In the cube
  five of them all point at the last stream's offset.
- The imitation headers carry `crc = 4x, compressed = x, size = 2x`, and a real stream's name.
  These are the "directory-like records" page 1 warned about, and the 6-byte scan pattern inside
  them is why the scan sees so many fake hits.

Correction: I first wrote the block as 69 to 84 bytes. That was wrong: I subtracted the 8-byte
offset base twice. The prove agent measured 85 to 100 and my rerun agrees.

## The key and the signatures

Measured:

- Unrelated files share their first four bytes: 15 pairs among 178 distinct files, 163 distinct
  values. In 15 of 15 pairs all three signatures are equal too. So the first four bytes select
  the signatures (`keyspace.out`).
- 15 pairs among 178 files puts the number of keys at roughly 1,000.
- 162 of 163 keys are four consecutive outputs of `rand() & 0xff` from the Microsoft C runtime
  generator (state × 214013 + 2531011, output bits 16 and up). A random 4-byte value is in that
  stream with chance 1 in 256 (`msvc2.out`, `msvc3.out`). The one that isn't is `82 5d 07 04`
  (C05 in the SW2022 set and online `10459a56`), with signatures `02045e80 04016e82 03087e78`.

Ruled out for the signatures (`relate.out`, `locate.out`, `prng.out`, `msvc4.out`, `head4.out`):
any XOR/rotate/shift map of the key or of each other, `a·x + c mod 2^32`, a copy elsewhere in the
file, the same `rand() & 0xff` stream within 20,000 calls either side of the key, MD5/SHA of the
key, common generators seeded with the key. The key is not a CRC-32 or Adler-32 of the file.
Each test has a control that finds a planted answer.

Guess, not checked: SolidWorks holds a table of about 1,000 keys with their signatures, built
once with `rand()`. It fits the small key count and the failed derivations. Nothing here proves
it. `table.json` holds the 163 entries seen so far.

## Blind checks

- **Prove** (`scripts/EXP112/prove/`, own Python parser and zlib): the directory holds on 181 of
  181 files, 8,015 entries with duplicates counted, 0 CRC or size mismatches, brute-force scan
  set equal to the directory, offsets from byte 0 match in 0 files. Five kinds of one-bit damage
  were each rejected in 181 of 181 files. It corrected the filler size (above) and pointed out
  that the directory size field runs past the last real record.
- **Disprove** (`scripts/EXP112/disprove/`): stopped by the usage limit, no verdict. Its partial
  outputs show one passing end record per file on 181 files, method 8 and flags 6 everywhere, and
  no valid stream outside the directory (`t1.out`, `t2.out`). Treat that as unfinished.
