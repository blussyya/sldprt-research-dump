# EXP-067 — NQ-043 answered: the post-`Z` field is `BODY.highest_node_id`

Date: 2026-09-22. Base: staging `d8fb034`.
Scripts: `scripts/EXP067/`. Reproduce:

```sh
node knowledge/evidence/scripts/EXP067/body-node-alignment.js
```

**Provenance.** This derives from the published Parasolid XT Format Reference
(`knowledge/PARASOLID_XT_SPEC_NOTES.md`) and is verified on our own corpus. It uses no code,
data or result from any other repository. The spec supplied the hypothesis; the corpus decides it.

---

## 1. What the spec says

Three statements, all from the document:

1. **`Z` terminates a per-node-type schema-delta edit script** (`C`opy / `D`elete / `I`nsert /
   `A`ppend, then `Z`). It is **not** a record boundary. What follows is the remainder of the
   *first node of that type*.
2. A node is `<nodetype> [<n_elts> when variable] <index> <fields…>`, and **index 1 is the root
   node**.
3. `struct BODY_s` begins:

   ```c
   int    highest_node_id;    // $d   <- first field
   union  attributes_groups;  // $p
   struct attribute_chains;   // $p
   union  surface;            // $p
   union  curve;              // $p
   struct point;              // $p
   struct key;                // $p
   double res_size;           // $f   "size box", normally 1000
   double res_linear;         // $f   linear precision, normally 1.0e-8
   ```

So the text after `Z` must read `<index> <highest_node_id> <6 pointer fields> 1e3 1e-8`. That is a
positional prediction with three independent parts, and the corpus can refute any of them.

## 2. It holds, on both corpora

| check | SW2022 | SW2011 |
|---|---|---|
| `index == 1` (root node) | **24/24** | **25/25** |
| `res_size == 1000` present | **24/24** | **25/25** |
| `res_linear == 1e-8` immediately after it | **24/24** | **25/25** |
| fields between the candidate and `res_size` | **9**, constant | **6**, constant |

```
SW2011 C00 tokens:  1 251 2 3 0 0 0 0 1e3 1e-8 0 4 0 1
SW2022 C00 tokens:  1 226 2 3 0 0 0 0 0 0 0 1e3 1e-8 0
```

**The SW2011 gap of 6 is the decisive detail.** The 2006 spec's `BODY_s` has exactly six pointer
fields between `highest_node_id` and `res_size`, and the 2006 spec's own worked example reads
`12 1 12 0 2 0 0 0 0 1e3 1e-8` — index 1, `highest_node_id` 12, six pointers, then the two named
doubles. Our SW2011 files reproduce that struct field-for-field.

SW2022 has **9**, three more pointer fields. That is not a contradiction, it is the mechanism: the
schema-delta edit script exists precisely to encode fields added since the base schema. The gap is
constant within each era and differs between them, which is what a versioned fixed struct requires
and what a coincidence would not produce.

**NQ-043 is answered. The field is `BODY.highest_node_id`.**

## 3. What this settles, and what it corrects

**EXP-060 was right about the constants and wrong about the boundary.** It read `1000.0` and
`1e-8` as "the transmit's size box and resolution" — correct, and the spec names them `res_size`
and `res_linear`. It then concluded *"this is a real record boundary, not an accidental
alignment."* It is not a record boundary; it is the middle of the BODY node. The right conclusion
was drawn from the right observation for the wrong reason.

**EXP-059's probe worked by accident, and the spec explains why.** It read a `u32be` at `Z+3`.
The spec notes small indices are stored specially in binary (2 bytes), so after `Z` come 2 bytes
of index and then the `int` field — landing exactly at `Z+3`.

**Everything EXP-064 and EXP-065 measured is consistent with this reading, and now explained:**

| observation | under `highest_node_id` |
|---|---|
| tracks topology *and* feature history (EXP-065) | node ids are allocated as the body is built and edited; a body carrying a deleted feature has a different high-water mark |
| C04 (`Cut-Extrude1`) 309 vs C05/C06/C11 (`Cut-Extrude2`) 286 | different edit histories, different id ceilings |
| invariant to dimension and position (legacy, 4/4 groups) | ids do not depend on geometry |
| not a byte or content count (identical file lengths, identical integer counts) | it is not counting the transmit at all |

**EXP-065's falsification of the "ID ceiling" reading does not survive, as that experiment itself
warned.** It used a crude proxy — the longest dense prefix of integers appearing anywhere in the
text — and found C15 (57 > 44) and C16 (369 > 355). That proxy counts every integer in the file,
including field values, not node ids. It falsified the proxy, not the field. EXP-065 flagged this
explicitly; the flag was correct.

## 4. What is still NOT established

The field is **identified**, not yet **verified against its own semantics**. Proving the value
equals the maximum `node_id` over the body's nodes requires enumerating entity records and reading
their `node_id` fields — the spec shows `node_id` is the first field of each entity struct. That
is the next step, and it is now a well-posed one.

One open puzzle worth keeping in view: `binary − text == SolidWorks face count` on 24/24 modern
pairs, 0 on 25/25 legacy. If both files encode the same body, the same `highest_node_id` should
appear in both. A plausible reading is that the two exports are separate transmit operations and
one of them re-tags face entities — but that is a hypothesis, not a measurement, and the legacy
delta of zero is not yet explained by it.

## Status

| claim | verdict |
|---|---|
| the post-`Z` field is `BODY.highest_node_id` | **established** — 49/49 on three positional predictions |
| `Z` is a genuine record boundary (EXP-060) | **withdrawn** — it ends a schema-delta edit script |
| `1e3` / `1e-8` are the size box and resolution (EXP-060) | **upheld**, and named: `res_size`, `res_linear` |
| the value is a node/topology count (EXP-060) | **withdrawn** — it is an id high-water mark |

| the value equals max `node_id` in the body | **not yet tested** — needs entity records |

No entity record has been decoded. That remains true.

## Note on the two repositories

`sldprt-priv-work` is a **separate line of work, by design** — it reads directly from the
application's memory while it saves. This repository stays clean: it never inherits findings from
there, and runs its own experiments on its own corpus.

The two experiment sequences are therefore independent and both now use EXP-066 and EXP-067 for
different work. That is expected, not a collision to reconcile; the numbers are per-repository.

What does flow between them is **direction, not evidence**. The memory-side work is pointer
material: it says where to look. A claim only becomes a result here when it has been re-derived
from our own files, by our own code.

This experiment is an example of that discipline, and of its limit. The hypothesis came from the
published spec — a primary source this repository holds in its own right
(`PARASOLID_XT_SPEC_NOTES.md`), not from the memory-side work. The corpus decided it. Had the
prediction failed on 49 files, it would have been recorded as a failure regardless of what any
other source claims.
