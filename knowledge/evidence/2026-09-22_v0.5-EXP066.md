# EXP-066 — Independent verification of parser v0.3, and the STL reference is deficient on 12 of 25 models

Date: 2026-09-22. Base: staging `6ce3c15`.
Scripts: `scripts/EXP066/`. Reproduce:

```sh
node knowledge/evidence/scripts/EXP066/legacy-geometry-truth.js   # is the legacy decode correct?
node knowledge/evidence/scripts/EXP066/inflate-differential.js    # hand-written DEFLATE vs zlib
node knowledge/evidence/scripts/EXP066/stl-reference-check.js     # the STL reference itself
```

`parser/v0.3` decodes SolidWorks 2011 OLE2 DisplayLists — the open question **NQ-038**. Its own
suite checks face counts and decoder parity, and `CORE_VALIDATION.md` says plainly what that does
not establish: *"Count agreement and decoder parity alone do not prove exact geometry."* This
experiment is that missing gate, plus two checks v0.3 could not run.

**Verdict: the legacy decode is correct.** Three of the four things I set out to break held up.
The fourth — the STL reference — broke, and it is the reference that is wrong, not the parser.

---

## 1. Legacy geometry against dimensions known in advance

v0.3's suite asserts legacy face counts against `BUILD_LOG_2011.md` and that a bounds record
exists. It never checks that a vertex is in the right place. These do.

| check | result |
|---|---|
| legacy mesh box == dimensions declared in the build spec (2e-5 m) | **7/7** |
| legacy mesh box == modern mesh box, geometry-matched models | **22/22** |
| per-face mesh inside its own stored INV-026 bounds, SW2011 | **145/145** |
| per-face mesh inside its own stored INV-026 bounds, SW2022 | **142/142** |

```
C00_cube_10mm          min[0.000000,0.000000,0.000000] max[0.010000,0.010000,0.010000]
C01_cube_20mm          min[0.000000,0.000000,0.000000] max[0.020000,0.020000,0.020000]
C02_cube_translated    min[0.050000,0.050000,0.000000] max[0.060000,0.060000,0.010000]
C14_sphere             min[-0.005000,-0.005000,-0.005000] max[0.005000,0.005000,0.005000]
C19_half_cylinder      min[-0.005000,0.000000,-0.005000] max[0.005000,0.010000,0.000000]
```

The nominal values come from the model names and the build specification, never from anything
the parser produced. A decode that merely parsed without throwing could not land a translated
cube at exactly `[0.050, 0.060]`.

The third check is the strongest, and it is not a restatement of the first two: the bounding
record and the vertex array are different regions of the stream, decoded by different code paths.
Worst excursion is **1.341e-9 m** — the same float32 vertex-resolution figure EXP-061 and EXP-064
reported. Consistent across three experiments and two container formats.

`C15_torus` sits 6 µm inside nominal on two axes. That is chord error on a tessellated curved
surface, which is the correct behaviour for an inscribed mesh, not a decode fault.

## 2. The hand-written DEFLATE is correct

`parser/v0.3/src/inflate.js` is 166 lines of hand-rolled DEFLATE, and it is the single largest
correctness risk in the commit. v0.3's suite compares *parser results* between it and Node's
zlib, which is weaker than it sounds: the parser reads a subset of the inflated bytes, so a
decoder that corrupted a region nothing parses yet would still pass.

Comparing the inflated **bytes**, over inputs chosen to reach paths the corpus may never contain:

```
synthetic + corpus comparisons : 672
  byte-identical to zlib       : 672
  mismatched or threw          :   0
  real corpus zlib members     : 272
```

Covered: stored blocks (level 0), fixed-Huffman (1–40 byte inputs), dynamic-Huffman with skewed
and two-symbol alphabets, 64 KiB of zeros for window wrap, period-258 for maximum match length,
period-32768 for maximum distance, 200 KiB incompressible random, and the empty input.

### One behavioural difference, and it was my harness that was wrong first

`inflate.js:158-160` reads the Adler-32 from `src[len-4]`, so the input must be **exactly one
zlib member**. zlib tolerates trailing bytes; this decoder does not.

My first run sliced `buf.subarray(i)` — the whole file tail — and recorded **272 "Adler-32
mismatch" failures**. Every one was the harness. Given the exact member, output was byte-identical
each time. The failed run is kept in the script's comments so the next person does not repeat it.

This is a precondition worth writing down rather than a defect: v0.3's own callers pass exact
streams. But it means `inflate.js` is **not** a drop-in for `zlib.inflateSync` in our evidence
scripts, several of which (`EXP060/legacy-partition.js`, `EXP064/legacy-bounds.js`) deliberately
inflate from a scan offset with trailing data. The error message misdiagnoses the cause: it says
Adler mismatch when the real fault is an unsliced input.

## 3. The browser test now has actually been run

`parser/v0.3/test/browser.js` had never executed — `WEB_VALIDATION.md` states Chromium was
unavailable and calls its UI claims *"implementation evidence, not browser-test evidence"*. That
was honest, and it is now unnecessary: Chromium is available here and **the test passes**.

```
Browser smoke passed: modern/legacy file input, external drop, PNG sheet, invalid input.
```

Verified end to end: the legacy demo reaching 11 faces; a modern file (C15 torus) loading as
`modern DisplayLists` with 1 face; a real `drop` event with an arbitrary filename decoding as
`legacy OLE2` with 11 faces; the contact sheet at exactly 1584×1058 with a `data:image/png`
download href; an invalid input reporting `Could not load` while leaving the previous model
displayed (`#r-faces` still 11); and **zero page errors**.

Playwright was installed outside the repository, so the zero-dependency tree is untouched.

## 4. The STL reference is missing whole faces on 12 of 25 models

`WEB_VALIDATION.md` reports that C04's supplied STL has no triangles on one cap — 38 in the
parser, 0 in the STL. **Confirmed independently**, reading the binary STL directly in Node with
no use of `compare-stl.py` or numpy, and taking the plane extremes from the parser's geometry so
the STL cannot set its own pass mark.

It is not one model. Across the whole legacy corpus:

| model | STL tris | parser tris | on z⁺ STL / parser | on z⁻ STL / parser |
|---|---:|---:|---:|---:|
| `C00_cube_10mm` | 12 | 12 | 2 / 2 | 2 / 2 |
| `C04_cube_hole_5mm` | 132 | 152 | **0 / 38** | 44 / 38 |
| `C05_cube_hole_3mm` | 126 | 128 | **0 / 32** | 42 / 32 |
| `C07_cube_two_holes` | 254 | 292 | **0 / 74** | 86 / 74 |
| `C10_cube_shell_1mm` | 20 | 28 | **0 / 8** | 2 / 2 |
| `C26_cube_hole_sw2011_native` | 132 | 152 | **0 / 38** | 44 / 38 |

**12 of 25 models have a plane the parser populates and the STL leaves empty**: C04, C05, C06,
C07, C08, C10, C11, C16, C17, C19, C20, C26.

The pattern is legible. Every plain cube (C00, C01, C02, C22) is exact at 2/2. The chamfer (C09)
is 3/3 and the split-line (C18) 4/4. **Every model carrying a through-hole or a shell loses a
cap** — which is precisely the set of models whose end face has an *inner loop*. The supplied STL
export drops planar faces with inner loops.

Two consequences:

1. v0.3's conclusion is right and stronger than stated: the reference is deficient, systematically
   rather than incidentally, so **triangle-level STL agreement is not a valid correctness gate on
   12 of 25 legacy models**. `WEB_VALIDATION.md` names only C04 in prose; the per-model data was
   already in `STL_RESULTS.json`, uncharacterised.
2. Our own parser produces the cap that the vendor's STL omits. The parser is the more complete
   record of the two on these models.

Totals reproduced: 73 files, **145 legacy faces**, **1,414 modern faces**, 88,518 triangles. The
145 matches EXP-064's independent count of 145 legacy bounding records exactly — two different
methods, two different code paths, same number.

## 6. Gaps to carry forward

Not defects in v0.3, but the repository is now inconsistent in three places:

- **None of the eight predictions in `PARASOLID_XT_SPEC_NOTES.md` §4 were tested.** The
  `knowledge/` tree is byte-identical to `f216801`, so this is provable rather than inferred.
  EXP-060's "`Z` is a genuine record boundary" claim — which the spec says is wrong, and which
  four experiments were built on — still stands unretracted.
- **The STL measurement was filed in `parser/v0.3/WEB_VALIDATION.md`, not `knowledge/evidence/`.**
  It is a corpus-wide measurement with counts, which `EVIDENCE_PRESERVATION_POLICY.md` places in
  `knowledge/`. This file now carries it.
- **The root `README.md` still says legacy OLE2 is unsupported throughout** and does not mention
  `parser/v0.3` at all. It contradicts a shipped capability that parses 25 legacy files.

Two smaller ones: `test/worker.js` prints its face counts rather than asserting them, so a
regression from 11 faces to 10 passes `npm test` while `WEB_VALIDATION.md` keeps claiming 11; and
the sheet panel still reads *"This page cannot start a download itself"*, inherited from the older
viewer, although `exportSheet()` now sets a `download` href.
