# EXP-116: reading face metadata in the other record layouts (NQ-071)

2026-11-24. The converter now reads face IDs and tags from SolidWorks 2025 and 2026 saves: 4,484
faces in 24 files that had none. The metadata was in the display record all along, 16 bytes earlier
than the reader looked, because those saves drop one empty array. All 4,484 join a native face and
carry the native face's surface type. The 140-byte layout (190 faces in 3 files) has no ID or tag in
its display record at all.

Measured, not blind-checked; the layouts themselves were found by two blind agents (EXP-099 and
EXP-110 checks). Scripts: `scripts/EXP116/`. Converter: `src/display.js` (`recordLayout`),
`test/display.test.js`.

## The layouts

| layout | how the reader tells it | files | faces |
|---|---|---:|---:|
| A | the `[8, 100, 2]` array at +132, as before | the rest | 13,533 with metadata |
| B | a float64 at +92 equal to twice the radius at +84, then the array at +140 | 3 | 190 |
| C | +128 is 0, +132 is the `1` flag, and a `[12, 100, 2]` array follows at +136 | 24 | 4,484 |

Each record is checked by its own structure, not by the file's version. One file saved at
DisplayLists 18000 (2025, `16f99cd7`) is all layout A, so the version can't decide it.

The user suggested the metadata might be elsewhere, for example in the ghost partition. For layout
C it isn't: it is in the display record, after the bounding record, where steps 2 onwards of the
surface record follow without step 1. For layout B the display holds none: after two empty
`[12, 100, 2]` arrays and a zero flag, the record ends with three nonzero words (2149384192, 12, 2 in
`7841a106`). Where those faces' IDs live, if anywhere, isn't known.

## Checks on layout C

| check | result |
|---|---|
| faces with metadata after the change | 4,484 (`layouts-after.out`); the agents' 4,432 plus 52 in the 2026 re-saves of controlled models |
| join to a native face (`display-join.js`) | 4,484 of 4,484: 4,219 by unique ID, 140 by type, 125 by geometry (`joinC.out`) |
| display tag equals the native surface type | 4,484 of 4,484 |
| control: every layout C ID shifted by +1, three parts | 1,973 of 2,080 find no candidate, 0 land on the same face (`joinC_ctrl.out`) |
| plane direction against the native plane normal | 194 planes in head_back's 2026 re-save, 435 in `2e6e140a`: at most 1.7e-6 degrees (`planes.out`) |

The tag match is partly built into the join (it filters candidates by type), which is why the
shifted-ID control matters.

## Effect on the converter

- Every face of head_back's 2026 re-save (535) and of `2e6e140a` (1,117) now has its ID and tag.
- Mesh STEP (`--mesh`) gets exact planes on these files: 435 on `2e6e140a` (exact STEP has 435
  PLANE entities too) and 194 on the head_back re-save, where both had none before
  (`meshstep.js`). Exact STEP is unchanged; it reads the B-rep.
- The golden display record changes for 45 files, only by the new `layout` field on each face's
  metadata. No other value changed (checked by comparing the old and new parse).
- `npm test`: 86 pass, 2 skipped (the OpenCascade ones), with a test for layouts B and C and two
  for EXP-115.
