# Parasolid XT Reverse-Engineering Ecosystem — Technical Intelligence Report

**Prepared for:** SLDPRT-format research project (currently decodes only `Contents/DisplayLists` tessellation; no native Parasolid B-rep parsing).
**Date:** 2026-09-20
**Method:** WebFetch against GitHub repos/raw files and the 13thmonkey.org PDF (fetched, saved locally, and text-extracted directly via zlib/PDF stream parsing since `pdftoppm`/`pypdf` were unavailable in-sandbox). All fetched material is treated as untrusted data. No instructions embedded in any fetched page were followed; none of the fetched pages contained agent-directed instructions except as noted below.

---

## 0. Executive summary

The ecosystem has **one real common ancestor**: the Siemens/UGS **"Parasolid XT Format Reference," October 2006**, a proprietary document marked confidential to UGS Corp, now mirrored on the third-party archive site 13thmonkey.org. Nearly every open-source XT reader either cites it, silently reproduces its language, or reimplements exactly the mechanism it describes. Two of the four repos (`ps-parser`, `parasolid-kit` via its "builtin profiles") also lean on schema data taken from real files or Siemens SDK installs, which is a separate and more legally exposed source than the 2006 PDF. The fourth (`xt-parser`) is described by its own project notes as built substantially from **Ghidra decompilation of Siemens' `pskernel.dll`**, i.e. independent reverse engineering of the binary, not the PDF — the most legally distinct but also least mature/tested of the four.

None of the four projects is production-grade. All are small, single/few-maintainer, low-star repositories. Only `parasolid-kit` shows conventional engineering maturity signals (fuzzing, CI, corpus tests, changelog).

## 2. How the XT format is actually decoded (from the primary source)

The Siemens/UGS **"Parasolid XT Format Reference," October 2006**, extracted directly from the PDF (title page text: *"Parasolid XT Format Reference / October 2006"*; footer: *"© 2006. UGS Corp. All rights reserved"*; body: *"NOTICE: All information contained herein is the property of UGS Corp. No part of this publication... may be reproduced, stored in a retrieval system, or transmitted... without the prior written permission of UGS Corp."*), describes the mechanism as follows. This is a **DEMONSTRATION** (verified against the raw PDF bytes, not a repo's claim about the PDF):

**File header:**
- A human-readable preamble (machine/OS/user/format/date fields), then a schema identifier and user-field size, then optional non-standard "Frustrum" data.
- Binary variants signal themselves with flag bytes: `'B'` (bare/machine-dependent binary), `'PS\0\1'` + a 3-byte machine descriptor (typed binary), or `'PS\0\0'` (neutral binary, big-endian IEEE floats).

**Node model:**
- The data is a flat stream of **nodes**, each with an integer **node type**, and each assigned a sequential **index starting at 1** as it is written; unused indices are permitted. Pointer/reference fields in later nodes are simply these integers (0 = null pointer). Quote: *"Every node in the XT data is assigned an integer index from 1 upwards (some indices may not be used). Pointer fields are output as these indices, or as zero for a null pointer."* The root node's type (index 1) depends on content: `BODY`, `ASSEMBLY`, `PART_XMT_BLOCK`, or `WORLD`. A terminator is a two-byte int `1` followed by index `0`.

**Schema-driven field decoding:**
- *"XT permanent structures are defined in a special language akin to C which generates appropriate files for a C compiler."* Each schema entry has a node header (`nodetype`, `name`, transmit flag, field count, variable-length flag) followed by one line per field (`field_name`, type code, transmit flag, node/pointer class, element count). Example given verbatim in the PDF: `29 POINT; Point; 1 6 0`.
- **Field type codes** documented: `u` unsigned byte, `d` 32-bit int, `f` double, `p` pointer-index (small indices ≤32767 as 2 bytes, large ones as a quotient/remainder pair), `v` 3D vector (3 doubles), `h` intersection point, `i` interval (low/high), `b` box (6 doubles).
- **Variable-length nodes**: last field has variable length; the length is written as an extra integer between the node type and the index. Worked example from the PDF: schema entry `83 REAL_VALUES; Real values; 1 1 1 / values; f; 1 0 1`, and a matching data instance `83 3 15 1 2 3` (node type 83, 3 elements, index 15, values `[1,2,3]`).
- **Unresolved indices**: an index field with no corresponding node in the file is treated as zero.
- **Pointer classes**: fields are typed to a *class* of node (a union of allowed node types) rather than one specific type, e.g. `attributes_groups` must be class `ATTRIB_GROUP_cl`, `owner` must be `POINT_OWNER_cl`.
- **Embedded/delta schemas (the backward-compatibility mechanism, and the origin of `sch_13006`)**: *"From Parasolid V14+, schema differences vs. base V13 (SCH_13006) are encoded inline."* New node types in a file are written out in full (field count, name/description, each field's name/type/ptr_class/n_elts/xmt_code); changed nodes carry an edit sequence (Copy/Delete/Insert/Append operations against the base schema); a flag byte `0xff` means "unchanged from base schema." The PDF spells the matching algorithm out explicitly: *"the number of 'effective' fields in the base schema node and the current schema node are assembled, where an effective field is either transmittable (xmt_code == 1) or variable-length (n_elts == 1)... If the two arrays match... output the flag..."* This is exactly the mechanism `ps-parser`'s README describes operationally ("resolves per-node schemas on the fly — handling files that embed full or delta schema definitions") without re-deriving the algorithm itself.

**Entity representations (verified field tables extracted directly from the PDF):**
- `PLANE`: struct alias `struct PLANE_s == ANY_SURF_s`; typedef `PLANE_s *PLANE`.
- `CYLINDER`: parametric form `R(u,v) = P + rXcos(u) + rYsin(u) + vA`. Fields: `pvec` (vector, point on axis), `axis` (vector, unit), `radius` (double), `x_axis` (vector, unit); Y axis = cross(axis, x_axis).
- `CONE`: Parasolid's cone is *half* a mathematical cone, axis points away from the used half. Parametric form `R(u,v) = P − vA + (Xcos(u) + Ysin(u))r + vtan(a)`. Fields: `pvec`, `axis`, `radius` (radius at pvec), `sin_half_angle` (double, truncated in extraction but present).
- `SPHERE`: `R(u,v) = C + (Xcos(u)+Ysin(u))rcos(v) + rAsin(v)`. Fields: `centre`, `radius`, `axis`, `x_axis`.
- `B_SURFACE` and NURBS curves/surfaces are represented via a `SURFACE_u`/`GEOMETRY_u` union system; `B_CURVE` (the NURBS curve type) stores degree, control vertices, weights, and a knot vector "stored as distinct knots + multiplicities" rather than a flat repeated-knot array.
- **Common curve fields** (shared by all curve node types): `node_id` (int), `attributes_groups` (pointer0), `owner` (pointer0, topological owner), `next`/`previous` (pointer0, geometry chain links), `geometric_owner` (pointer0), `sense` (char, `'+'`/`'-'`).
- **Topology entity set** named explicitly: `WORLD`, `ASSEMBLY`, `INSTANCE`, `BODY` (solid/sheet/wire/general manifold types), `REGION` (solid/void flag + shell set), `SHELL`, `FACE`, `LOOP`, `HALFEDGE` (oriented edge use — Parasolid's "fin"), `EDGE`, `VERTEX`.
- **Numeric tolerances stated as defaults**: *"points are not considered coincident unless they are less than 1.0e−8 units apart (linear resolution). Directions are considered parallel if they differ by less than 1.0e−11 radians."* Geometry must fit inside a size box of ±1000 units (1 km at 1 m default unit).

This is a complete, self-consistent, and (from the extraction) internally coherent account: an engineer could implement a basic XT reader directly from this document's node-index/field-type/variable-length/embedded-schema description without any other source, **provided they also have, or can derive, a schema table** (see §3 — the document describes the mechanism for reading/patching schemas but a working base schema like `sch_13006.s_t` is a separate artifact from the mechanism description).

## 3. Schema availability — the crux

Parasolid schemas are Siemens' property; the 2006 PDF is explicit and severe about this (full reproduction, storage, or transmission prohibited without written permission). Given that, here is where each project actually gets usable schema data, and what that implies:

| Route | Who uses it | What it means |
|---|---|---|
| **Embedded in the XT stream itself** | All binary-XT readers, by necessity | The XT format's own backward-compatibility mechanism (§2) means a file *can* carry enough delta information to self-describe new/changed node types relative to a stated base schema. This does not eliminate the need for a *base* schema (e.g. 13006) to diff against — it only reduces how much of the base schema must be sourced externally, and only for nodes the file's schema version doesn't change. |
| **Shipped as a repo asset** | `ps-parser` (`assets/sch_13006.s_t`) | Ships a plain-text base schema for schema id 13006 under the repo's blanket MIT license, without stating where the file itself came from. Internal evidence (the schema id matches the exact base-schema version the Siemens PDF names for V13/V14+ delta encoding, and the file's syntax matches the PDF's schema-file grammar exactly) makes it very likely this is a genuine extracted Siemens schema table, not an invention — but the repo does not say whether it was hand-derived from Siemens SDK material, extracted from an installed product, or obtained some other way, and it license-labels the whole repo (including this file) MIT without carving out the schema asset. |
| **Derived from the 13thmonkey PDF** | `xt-parser`'s `xt-reference.md` (structurally/textually), and by strong inference `13thmonkey.org`'s own hosting | The PDF documents the *mechanism* for reading schemas, and gives partial example schema fragments (e.g. the `POINT`/`REAL_VALUES` examples), but is not itself a full machine-usable schema table for any one schema version — it's prose+examples, not a ready-to-parse `.s_t` file. |
| **User obtains it themselves from a Siemens-licensed product** | `parasolid-kit` (explicit policy: *"Siemens catalogs are not included... Obtain the matching catalog from a Parasolid SDK or a Parasolid-based product available to you"*) | This is the most legally conservative stance among the four: the repo distributes code and a mechanism, but pushes the actual Siemens-owned catalog data back onto the user, who is presumed to already hold a Parasolid/SDK license. Its own "built-in profiles" are instead schema keys the authors say they extracted themselves from specific products (Onshape, iCAD, SolidWorks partitions) rather than distributing Siemens' catalog files verbatim. |
| **Reverse-engineered from the compiled kernel** | `xt-parser`'s sibling/predecessor material in `CLAUDE.md` ("xt-winnow"), via Ghidra decompilation of `pskernel.dll` | Distinct from all of the above: this route derives format knowledge from behavior of the compiled binary rather than from any Siemens document, embedded schema, or another repo. It is also the route with the least public documentation/tests of the four sources, resting on the fetched summary of a project file rather than on inspectable output in this survey. |

**Licenses actually stated, factually:**
- `parasolid-kit`: MIT AND Apache-2.0 (code); explicitly excludes Siemens catalog data from what it distributes.
- `sldkit`: MIT for pre-0.2.0 material; **PolyForm Noncommercial 1.0.0 + separate UnRobotics commercial license** for new material from 0.2.0 on.
- `ps-parser`: MIT, applied blanket-wide including the shipped `sch_13006.s_t` asset, with no separate provenance statement for that asset.
- `xt-parser`: no license file/statement found in the fetched page.
- The 2006 Siemens/UGS PDF itself: explicitly **proprietary**, all rights reserved, reproduction/storage/transmission prohibited without written permission — it is not under any open license, and its presence on 13thmonkey.org is a third-party mirror, not an authorized Siemens release. (This report does not offer legal advice on the effect of that prohibition on downstream projects; it only records what the document and repos state.)

## 4. Provenance audit

Classifying each project's format knowledge as **(A) independently verified against real files with tests/fixtures**, **(B) inherited** (from the 2006 PDF / 13thmonkey, from Siemens SDK docs, from each other, or from ODA), or **(C) asserted without support**:

- **`parasolid-kit` — mostly (A) with some (B).** Has a `corpus/` directory, fuzzing, CI, and documented "resource-validation," "step-accuracy," "nurbs-surface-evidence," and "rational-periodic-surface-evidence" pages with paired JSON data files — i.e., it claims to validate against real files and cross-checks (STEP accuracy comparisons). Its "built-in profiles" for Onshape/iCAD/SolidWorks are (A)-style (extracted from real products) by its own description, though this survey did not independently inspect the underlying evidence files. No citation of the 2006 PDF or of the other three projects was found in what was fetched, so no direct (B)-from-each-other lineage is confirmed for this repo specifically (absence of evidence, not evidence of absence — the docs tree wasn't fully read).
- **`sldkit` — (B), openly.** Explicitly inherits its Parasolid capability from `parasolid-core`/parasolid-kit as a dependency; its own novel contribution is the SLDPRT container layer, which it separately claims (A)-style testing (cargo tests, pytest, CI wheel checks) for the metadata/tessellation/B-rep-linkage parts it implements itself.
- **`ps-parser` — mixed (A)/(B)/(C).** The node/schema decoding mechanism it implements matches the 2006 PDF's documented algorithm closely (a form of (B) inheritance, though the README does not cite the PDF — this survey infers the match from independently re-deriving the PDF's algorithm text, not from the repo's own citation). The `sch_13006.s_t` asset is very likely a real Siemens artifact by internal consistency (schema-id match, syntax match) but its immediate source is undocumented — that specific gap is (C), asserted without support, even though the artifact itself looks authentic. No stated tests/CI, so there is no (A) validation evidence visible in the repo for its parsing correctness.
- **`xt-parser` — split personality.** `xt-reference.md` reads as (B) — inherited, and apparently very closely tracking (in places reproducing) the proprietary 2006 PDF's own text, without the repo stating that lineage. The `CLAUDE.md`-described "xt-winnow" work is a different, more evidenced strand: (A)-leaning claims (*"1000 ABC models: 1000/1000 parse OK... 947/1000 STEP match"*), but sourced from Ghidra reverse engineering of the compiled kernel plus an internal reference manual and a local SolidWorks schema file — i.e., independent-of-the-PDF reverse engineering, not inheritance from it. The publicly-visible `xt-parser` repo itself (4 commits, WIP alpha, no CI) shows no (A) evidence of its own.

**Cross-citation check:** none of the four fetched repos was found, in the pages actually retrieved, to explicitly cite any of the other three or the 13thmonkey PDF by name/URL. The **inheritance is textual/structural, not attributed** — i.e., this survey infers a common ancestor by independently re-deriving the 2006 PDF's own algorithm and entity-table language and finding it recur (in `xt-parser`'s reference file, and in the mechanism `ps-parser` implements), not by finding any repo say "we got this from 13thmonkey" or "we got this from parasolid-kit." Treat the "common ancestor" conclusion below as this survey's structural inference, not a claim any repo makes about itself.

**Is the 13thmonkey PDF the single common ancestor of most of this ecosystem?** Largely yes, **for the format mechanism** (node/index/pointer/variable-length/embedded-schema encoding, and the analytic surface field tables) — that mechanism, verified directly from the PDF bytes, is exactly what `xt-parser`'s reference file reproduces and what `ps-parser`'s described behavior implements, with no other public source offering the same level of mechanistic detail. It is **not** the source of the actual schema *data* (the `sch_13006.s_t` table itself, or `parasolid-kit`'s per-product profiles) — those come from real files/products/SDK installs, a separate and more Siemens-IP-adjacent lineage.

**How authoritative is the PDF?** It is **genuine Siemens/UGS internal documentation, not community-authored** — verified from the extracted PDF text itself: title "Parasolid XT Format Reference," dated **October 2006**, address "Parker's House, 46 Regent Street, Cambridge CB2 1DB" (Parasolid's historical home before/around the UGS/Siemens transition), copyright "© 2006. UGS Corp. All rights reserved," and an explicit proprietary/confidentiality notice. It predates Siemens' 2007 acquisition of UGS (hence "UGS Corp." branding rather than "Siemens"). It is **not an official public release** — it is hosted on a third-party archive (13thmonkey.org) that collects hard-to-find CAD format documentation, which strongly implies it circulated outside its intended (licensed-customer) distribution. It documents a specific, fairly old Parasolid generation (the V13/V14+ delta-schema discussion and SCH_13006 base schema place it around Parasolid v13–v14-era kernels, materially older than "current" Parasolid). Newer entity types, revised bitfield/compression schemes, or schema numbers well past 13006 would not be covered by it.

## 5. Feasibility assessment for us (zero-dependency Node.js, no npm packages)

**Is a schema file required, or is the stream self-describing enough?** Practically, **yes, a base schema (or a schema derived by other means) is required** for anything beyond trivial cases. The XT delta-schema mechanism (§2) lets a *specific* file be almost self-describing about node types it added or changed versus a stated base — but "versus a stated base" is exactly the problem: without that base table, an unchanged node's field layout is signaled by a flag byte (`0xff`) meaning "no change," which tells you nothing about what the layout actually *is*. So a reader needs, at minimum, one working schema (the specific one attached to the base version referenced) to bootstrap from. The good news for our target cases: `PLANE`, `CYLINDER`, `CONE` are exactly the surface types whose field layouts are fully spelled out, verbatim, in the public-domain-adjacent 2006 PDF text extracted in §2 above (field names, types, and geometric meaning), and they are simple fixed-length structs (a handful of vectors/doubles/a node_id) — no bitfields were found documented for these entities in the PDF (the header's binary-flag byte is the only bitfield-like element identified; entity fields themselves are typed as plain `d`/`f`/`v`/`p` etc., not packed bitfields). That materially lowers the bar versus, say, NURBS surfaces, whose knot/multiplicity/weight encoding is more involved.

**What would a minimal reader cost us?**
- **Header/preamble parsing + node/index walking**: straightforward, a few days. The mechanism (§2) is simple to implement in pure JS: sequential node records, integer node-type + index, pointer fields as plain integers resolved by index lookup, one flag byte for "unchanged" schema entries.
- **Schema bootstrapping**: this is the actual gating item, not the code. We would need a working base schema table (field names/types/order per node type) for whatever Parasolid version the SLDPRT's embedded partition uses. Options, roughly in order of legal cleanliness and effort: (a) derive our own table purely from the 2006 PDF's documented field tables for the small set of entity types we actually care about (plane/cylinder/cone/loop/edge/vertex/face) — cheap, narrow, and grounded in a document whose relevant text (§2) is factual geometric/structural description rather than Siemens' literal schema-table bytes; (b) obtain/derive a schema from a Parasolid SDK install if one is legitimately available to the project; (c) reuse a shipped `.s_t` asset such as ps-parser's, which raises the licensing questions in §3 that we would need to resolve for ourselves, not inherit as settled. We should not assume we can freely redistribute or depend on `sch_13006.s_t` without resolving that question first.
- **Entity decode for plane/cylinder/cone + trimming loops**: once schema/field layout is known, decoding these specific analytic surfaces plus their bounding loop/edge/vertex topology (LOOP → HALFEDGE → EDGE → VERTEX, all documented with field tables in the PDF) is a modest, well-scoped task — these are exactly the surface types the PDF documents most completely and that match our current `4001`/`4002`/`4003` tags.
- **Hard parts**: (1) correctly handling the embedded delta-schema patching logic for whatever specific Parasolid version generated the file (edit-sequence Copy/Delete/Insert/Append against a base schema is non-trivial book-keeping, even though each operation is simple); (2) NURBS/B_SURFACE support, which needs knot-vector and control-net handling well beyond plane/cylinder/cone, and which none of the four projects has demonstrated with independent test evidence in what we fetched; (3) validating correctness without a trusted independent oracle — we would want to cross-check against our own already-decoded DisplayLists tessellation and edge-ID topology (INV-018 through INV-024 in our own knowledge base) the same way we validated the display-list decode, rather than trusting any of these four projects' claims outright.

**Rough effort band and first milestone.** For a zero-dependency Node.js implementation limited to plane/cylinder/cone plus their trimming loops (not NURBS, not the full entity graph): this reads as a **multi-week, not multi-day, effort** — plausibly on the order of **2–5 weeks** of focused work for a first working reader against one known Parasolid/schema version, given we'd be deriving/validating a minimal schema ourselves rather than trusting an unverified shipped one, plus building our own cross-validation harness (as we did for DisplayLists). The **first milestone** should be: locate and length-delimit the embedded Parasolid partition inside the SLDPRT container (likely `Contents/Config-0-Partition`, currently noted in our own README as "unreadable/high entropy" — resolving that, e.g. checking for compression, is itself possibly step zero), read its header/preamble far enough to identify the schema id and confirm whether it matches a documented base like 13006, and successfully walk the node stream far enough to enumerate node types and counts without yet resolving all fields — mirroring exactly how we validated DisplayLists incrementally (header recognition → structural counts → field semantics → cross-checks), rather than attempting full B-rep reconstruction on the first pass.
